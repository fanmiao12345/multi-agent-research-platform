# 交付格式与报告模板：设计方案与开发计划

更新：2026-09-22。性质：**用户明确新增范围**（[主计划](PROJECT_MASTER_PLAN.md) 2.2 原本把"DOCX 输入/导出"列为本轮不做）。
本文只做设计与排期，**不代表已经实现**；实现进度记到 [实施清单](IMPLEMENTATION_TRACKER.md)，
每步证据记到 [实施日志](IMPLEMENTATION_LOG.md)。

## 1. 需求与范围登记

用户 2026-09-22 要求：① 导出格式可让用户选择 **.md / .docx / .txt**；② 先设计并定下**报告模板**；
③ 给出更多**对用户友好的策略**；④ 列入后续开发计划。

范围判定（按主计划第 9 节"新增需求必须说明是既定目标的遗漏，还是新增范围"）：

| 项 | 判定 | 依据 |
|---|---|---|
| DOCX **导出** | **用户新增范围** | 主计划 2.2"不列为本轮必做"清单含"DOCX 输入/导出"，本次由用户明确要求加入 |
| TXT 导出 | 用户新增范围（低成本） | 同上（原只承诺"Markdown 与安全 HTML 预览/导出"） |
| 报告模板与版式 | 用户新增范围 | 原计划只要求"必需章节可作硬约束"，未规定统一版式 |
| 导出"保留等级与局限" | **既定目标的遗漏，需补回** | D9-03 完成证据写明"导出保留引用、**等级与局限**"，当前导出只有正文 |
| DOCX **输入** | 仍不做 | 用户本次只要求导出；OCR / 复杂表格仍不做 |

不在本设计内：PDF 导出（打印友好可先覆盖）、表格与图片排版、云端共享、对外发布、DOCX 解析。

## 2. 现状基线（2026-09-22 实测）

| 位置 | 现状 |
|---|---|
| 后端 | `GET /api/jobs/<id>/artifacts/<aid>/download` → 附件下载，`Content-Type: text/plain`，文件名取登记产物名（如 `report.v1.md`）；`GET /api/jobs/<id>/export.html` → 把 Markdown 包进 `<pre>`，文件名 `report.html` |
| 前端 | 任务详情右上「下载Markdown」「导出HTML」；"版本与改稿"里旧版本只有「查看」 |
| 覆盖范围 | 只导出**最新**的 report/analysis/collection；只有正文，**不含**交付等级、局限说明、证据清单、来源清单、审校记录 |
| 命名 | `<kind>.v<n>.<ext>`，如 `report.v2.md`——对用户不友好、同名覆盖风险 |

## 3. 目标与约束

- 用户要在任务详情里**选择格式与内容范围**，拿到命名可读、可直接归档或转交的文件。
- 模板分两层：**必需骨架**由程序层保证（标题、一句话结论、元信息、局限、参考来源），**主体章节**仍由任务提纲自适应；
  用户的硬约束（必需章节 / 禁语 / 关键事实）优先，不被模板覆盖。
- 导出是**只读派生层**：不改执行语义、不改证据与交付等级判定、不新增对外副作用。
- 延续项目风格：能零依赖就零依赖；沿用 S5-09 写接口与路径安全策略。

## 4. 导出格式设计

### 4.1 用户可选项（EX）

| ID | 内容 | 说明 |
|---|---|---|
| EX-01 | 格式选择 UI | 任务详情「导出」下拉：Markdown / Word / 纯文本；记住上次选择（localStorage）；导出中显示进度与结果 toast |
| EX-02 | `.md` 规范 | UTF-8 **无 BOM**；`#`/`##`/`###` 层级；引用统一半角 `[E-001]`；`-` 列表；文件头为元信息块 |
| EX-03 | `.txt` 规范 | UTF-8 **带 BOM**（Windows 记事本/WPS 打开不乱码）；标题用「一、」「（一）」层级；列表用「· 」；引用仍写 `[E-001]` 便于检索；软换行≈100 字符 |
| EX-04 | `.docx` 规范 | **零依赖最小 OOXML**（`zipfile` + XML 手写：`[Content_Types].xml`、`_rels/.rels`、`word/document.xml`、可选 `docProps/core.xml`）；标题用 run 字号+加粗模拟（不依赖 styles.xml），正文段落、1.5 行距、页边距 2.54cm、列表用符号前缀 |
| EX-05 | 文件名规则 | `<任务短名≤40字>_<等级>_v<版本>_<YYYYMMDD-HHmm>.<ext>`；净化 `\ / : * ? " < > \|` 与控制字符；任务名空则回落 `job_<前8位>`；**中文名用 RFC 5987 `filename*=UTF-8''…`**，同时给 ASCII 回退名 |
| EX-06 | 内容范围开关 | 附录 A 证据清单 / 附录 B 来源清单 / 附录 C 执行说明；默认"含来源清单"，其余默认关 |
| EX-07 | 任意版本导出 | "版本与改稿"每行加「导出」；后端复用下载逻辑，按 `artifact_id` 指定版本 |
| EX-08 | 打包导出 | `zip`：报告 + 附录 + `evidence.json` + `sources.json`（可选来源全文）；用于归档或转交 |
| EX-09 | 复制而非下载 | 「复制全文」「复制交付说明」到剪贴板（贴进飞书/邮件/Word 的常见路径） |
| EX-10 | 接口形态 | `GET /api/jobs/<id>/export?artifact_id=&format=md\|txt\|docx&template=brief\|standard\|full&appendix=evidence,sources,process`；**保留**现有 `/artifacts/<aid>/download` 与 `/export.html` 不删（旧链接与测试继续可用） |

`.docx` 两条路线（需用户拍板，见第 8 节）：

| 路线 | 优点 | 代价 |
|---|---|---|
| A. 标准库最小实现（推荐先做） | 零新依赖、完全可控、可离线 | 只支持标题/段落/列表/加粗；目录、页码、表格、图片需后续加 |
| B. 引入 `python-docx` | 版式保真、目录/页眉页脚/表格/图片都好做 | 新增第三方依赖，需改 `pyproject.toml` 与 `requirements.lock.txt`，与项目"零依赖优先"风格冲突 |

### 4.2 安全与合规（沿用 S5-09）

- 只允许导出**任务内登记**的产物与证据；文件路径继续走 `resolve_under` 边界校验。
- 文件名净化后再拼 `Content-Disposition`，避免路径穿越与响应头注入。
- 响应带 `X-Content-Type-Options: nosniff`；docx 为二进制并不做预览渲染。
- 导出只读，不修改 `workspaces/` 内任何文件；不打印密钥或完整接口地址。

## 5. 报告模板 v1

### 5.1 骨架（TP-01，程序层保证）

```
<标题>
【一句话结论】≤80 字，直接回答任务目标
【元信息块】
【主体章节】按任务提纲组织；用户必需章节必须出现
【局限与未决问题】必须存在（缺口、无法判断项、覆盖范围）
【参考来源】按引用顺序自动生成
【附录 A 证据清单】可选
【附录 B 来源清单】可选
【附录 C 执行说明】可选
```

模板示意（标准版，Markdown 形态）：

```markdown
# 月度综述：Agentic RAG 的落地路径

> 一句话结论：三份周报指向同一方向——先做证据可核查的检索层，再谈自动化程度。

## 交付信息

- 任务目标：整理三份周报，写一份带引用的月度综述报告
- 交付等级：成品（accepted）｜版本：v2（改稿自 job_aaa…）｜生成时间：2026-09-22 17:30
- 执行方式：统筹者-工作者（Manager-Worker）｜模型：deepseek-v4-flash
- 引用：3 条（未解析 0）｜来源：可用 2 / 总 2｜用量：9 次调用 · $0.041 · 142.5s

## 一、结论摘要

本月的三份周报都指向同一方向：先做证据可核查的检索层 [E-001]〔事实〕。

## 二、依据与分歧

- 检索质量是第一瓶颈 [E-001]〔事实〕
- 评测口径尚未统一：两个团队用了不同的命中率定义 [E-002]〔事实〕

## 三、局限与未决问题

- 样本仅覆盖 8 个内部场景，不能外推到全部业务线 [E-003]〔事实〕
- 命中率口径统一后需要重新比较一轮〔未知〕

## 参考来源

1. 第 2 周周报（src_ab12cd）· 第 3 段 · 获取时间 2026-09-22
2. 第 3 周周报（src_ef34gh）· 第 5 段 · 获取时间 2026-09-22
```

### 5.2 模板条目

| ID | 内容 |
|---|---|
| TP-01 | 必需骨架：标题 / 一句话结论 / 元信息块 / 主体章节 / 局限与未决问题 / 参考来源 |
| TP-02 | 元信息字段：任务目标、交付等级、版本与谱系、生成时间、模式与执行方式、来源可用数、引用与未解析数、费用与用时、模型 |
| TP-03 | 事实标注沿用〔事实〕〔推断〕〔未知〕；冲突保留双方归属，不合并成单一结论 |
| TP-04 | 模板档位：**简报版**（结论 + 3~5 要点 + 局限 + 来源）/ **标准版（默认）** / **完整版**（标准版 + 附录 A/B/C） |
| TP-05 | 版式参数：docx 标题 16pt 加粗、小标题 14pt、正文 11pt、1.5 行距、页边距 2.54cm、中文等线/宋体 + 西文 Calibri；txt 见 EX-03；md 保持纯 Markdown 交由阅读器渲染 |
| TP-06 | 与硬约束的关系：导出前复验必需章节 / 禁语 / 关键事实；未通过时文件头显式标注"草稿：未通过项 …"，**不允许**把 draft 伪装成 accepted |

## 6. 对用户更友好的策略（UX，按主题分组）

### 6.1 拿到文件（P1 优先）

| ID | 策略 | 为什么 | 成本 |
|---|---|---|---|
| UX-01 | 文件名可读 + 中文不乱码（EX-05） | 现在 `report.v1.md` 分不清是哪个任务、多个任务互相覆盖 | 小 |
| UX-02 | 导出即带交付信息（等级/局限/来源/花费） | 补齐 D9-03 承诺；用户转交时不需要另外解释 | 小 |
| UX-03 | 一键复制交付说明 | 多数人最终是贴进飞书/邮件，复制比下载快 | 小 |
| UX-04 | 打印友好 + 浏览器 Ctrl+P 出 PDF | 不想加 PDF 依赖也能满足"要 PDF"的诉求 | 小 |

### 6.2 读得更舒服（P2）

| ID | 策略 | 为什么 |
|---|---|---|
| UX-05 | 详情页"摘要优先"：顶部先 TL;DR + 3 条要点，全文折叠 | 用户多数只看结论，长报告容易劝退 |
| UX-06 | 阅读器目录锚点、字号/宽度切换 | 8000+ 字报告需要定位与可读性 |
| UX-07 | 改稿快捷模板：更短 / 更学术 / 面向非技术读者 / 补齐引用 | 降低"不会再写提示词"的门槛，改稿成功率更高 |
| UX-08 | 未解析引用一键列出 + 明确标注"哪些结论暂缺依据" | 直接服务"关键结论均有依据"的验收标准 |
| UX-09 | 版本对比（v1↔v2 差异高亮）+ 改稿说明随导出附带 | 改稿类任务的核心诉求是"改了什么" |

### 6.3 归档与复用（P3）

| ID | 策略 | 为什么 |
|---|---|---|
| UX-10 | 待补充输入给候选项（可点选，少打字） | 现在纯文本框，用户不知道该写什么 |
| UX-11 | 导出历史（最近导出可重复下载） | 反复找同一个文件很烦 |
| UX-12 | 跨任务搜索（目标 + 报告全文） | 任务积累后，找"上次那份 RAG 报告" |
| UX-13 | 自动归档备份（workspaces → 按周 zip，尽力而为不静默） | 与 ops/backup 呼应，防误删 |
| UX-14 | 移动端阅读与导出优化、键盘快捷键 | 手机上看结果、快捷新建/刷新/导出 |

## 8. 风险、依赖与待拍板

| 编号 | 风险/决策 | 处理 |
|---|---|---|
| R1 | docx 保真度：零依赖实现只有标题/段落/列表/加粗 | P1 先做最小可用；目录/页码/表格/图片列为 P3+ 可选；Word 与 WPS 各验收一次 |
| R2 | 依赖策略：引入 `python-docx` 与"零依赖优先"冲突 | **待用户拍板**（路线 A 先做，路线 B 需明确同意并同步 requirements） |
| R3 | 中文文件名在旧客户端乱码 | RFC 5987 + ASCII 回退名；浏览器自检覆盖 |
| R4 | 大报告（>2MB）转换耗时 | 流式写 zip、限制单文件大小；P1 前先测 2MB 基准 |
| R5 | 模板骨架与自适应提纲冲突 | 用户必需章节优先；冲突在导出文件中标注，不静默覆盖 |
| R6 | `.txt` 加 BOM 与 `.md` 不加 BOM 的取舍 | 默认按 EX-02/EX-03 执行，**待用户确认** |
| R7 | 导出内容可能含敏感业务原文 | 只导出用户自己任务内的文件；文件名与内容不写入日志；与"发送哪些内容"说明保持一致 |

**需要用户拍板的 3 项**：① docx 路线（A 零依赖 / B python-docx）；② 默认模板档与附录默认值（建议：标准版 + 只带来源清单）；
③ P1 是否与 Q4-02 合并（建议合并，一次改完再复验）。

## 9. 与其他文档的关系

- **主计划 2.2**："不列为本轮必做"中的 `DOCX 输入/导出` 拆为「DOCX 输入（仍不做）」与「DOCX 导出（用户新增，见本文）」，并在 §11 登记新增范围。

- **优化清单 O-13 等回归**：导出属只读派生层，不改执行语义，不需要重跑 Q2/Q3 真实批次；但任何触及报告正文生成的模板改动都按功能变更处理，另记版本并复验。
