# 个人 AI 智能体系统：完整目标与开发总计划

版本：2026-09-11 / v1。性质：用户要求的开发主线重整；本文是目标、范围与实施顺序的唯一主计划。

本次只更新开发文档，不表示下列功能已经实现。逐步状态见 [IMPLEMENTATION_TRACKER.md](IMPLEMENTATION_TRACKER.md)，实际证据见 [IMPLEMENTATION_LOG.md](IMPLEMENTATION_LOG.md)，当前入口与缺口见 [EXECUTION_STATUS.md](EXECUTION_STATUS.md)。

## 1. 最初目标与本次方向确认

### 1.1 整体目标

做一个基于现有 LangGraph 运行时、在本机使用的个人 AI 智能体系统：用户提出工作目标，系统理解任务、选择合适的执行方式、安排单个或多个智能体、调用工具获取材料、交接阶段成果、检查完成情况，最后交付可用且可追溯的结果。

用户不必充当项目经理，不必逐次决定调用哪个工具、创建几个智能体、安排谁先做谁后做。系统应当在预算和权限范围内自行推进；过程可查，但不是用户必须逐步操作的界面。

原始工程目标是统一 Agent Harness：不同角色、工具、技能和协作方式共享运行、上下文、权限、账本、状态、恢复与产物机制。不能给每种模式另造一套互不相通的应用。

### 1.2 第一个完整落地场景

资料整理与研究写作是用户明确选择的第一类真实工作，用它贯通整个系统：已有资料整理、主题研究、比较分析、依据材料核查说法、报告写作、追问改稿与更新。

固定研究链是候选执行方式和可复用的业务能力，不再作为产品全部目标。单智能体可以直接完成简单工作，多智能体可以分担独立子题或专业角色。新增其他行业应用不在本轮范围内。

### 1.3 用户决定与实施默认值分开记录

| 项目 | 约定 | 来源/性质 |
|---|---|---|
| 核心体验 | 一次输入目标，系统自动选型并执行，交付时告知方式、依据、花费和等级 | 用户已明确 |
| 过程展示 | 进度和过程记录可查看，内部细节默认收起 | 用户已明确 |
| 询问用户 | 超出已授权预算，或缺少无法合理默认的关键业务条件时暂停；其余按可见默认值推进 | 用户已明确 |
| 可选计划确认 | “先看计划再开始”默认关闭；用户打开时遵循该选择 | 已有交互约定 |
| 嵌套分工 | 子智能体可以继续拆分，但不得自行扩大权限和预算 | 用户已明确 |
| 默认预算规则 | 同等任务规模下最省与最贵模式的典型成本取中点；用户显式预算优先 | 用户已明确规则；数值在 Q3 校准 |
| 先开发后优化 | 全部范围内功能实现并接通后，才进入整体测试、真实质量评测与优化 | 用户本次明确要求 |
| 初始规模 | 来源最多 20、正文每份 2MB/合计 10MB；嵌套深度 2、派生总数 12、并发最多 3 | 继承现有计划的实施默认值，非实测最优值 |
| 关键条件清单 | 首版只包含缺失后无法确定任务对象/范围的条件，例如未指明比较对象 | 实施默认清单，Q4 根据实际使用集中修订 |

预算中点的计算不能把简单问答与复杂研究混为同一种规模。D 阶段采用明确标注的配置估值，不能声称已测得最佳阈值；未知价格不能算成免费。

## 3. 最终用户流程与不同工作方式

### 3.1 默认流程

1. 用户输入目标；可附资料、原稿、读者/长度、网络策略、预算与时限。
2. 创建根任务，检查配置和授权范围，继承所属会话的有效材料。
3. 理解目标及输出要求；只有不能合理默认的关键条件才向用户补问。
4. 判断资料是否充足，选择 single/fixed 或多智能体方式，生成版本化计划。
5. 在根预算内派工；按需搜索、读取资料、调用工具、检索已授权知识。
6. 按依赖交接结构化成果，保留原始出处；独立工作可有界并发。
7. 检查任务覆盖、证据支持和冲突；有明确缺口时有限补搜、重规划或修改。
8. 达成要求则交付；能力/资料不足、预算不足、取消或故障时交付对应说明和已有产物。
9. 展示结果、依据、执行方式和一句理由、总花费/未知项、等级；详细过程按需展开。
10. 用户追问时继续同一会话，建立新版本；来源变更后重做受影响部分，保留旧版本。

### 3.2 工作方式

| 方式 | 使用条件 | 执行内容 | 不得偷换的含义 |
|---|---|---|---|
| single | 简单问答、计算、单点处理 | 一个执行体按需调用工具并交付 | 不应强迫简单计算也跑完整写作链 |
| fixed | 输入和步骤清晰 | 固定阶段整理、成稿、审校 | 是候选与保底路径，不是整个系统 |
| manager_worker | 任务需先拆解，子任务有依赖或不同职责 | 统筹者安排任务、验收成果、继续派工 | 不能只传角色名称而不传前置成果 |
| fanout | 两个以上独立子问题 | 有界并发执行，收齐结果后汇总 | 开线程但模型请求串行不能标并行完成 |
| dynamic_team | 执行中发现新缺口，需要调整分工 | 根据阶段证据有限增加/替换子任务并重验计划 | 不能无限生成新任务或改掉用户目标 |
| debate | 需要比较有依据的正反观点 | 分别整理观点与证据，审查支持关系、保留争议 | 智能体投票或意见一致不能替代事实核实 |

资料网络策略：仅依据给定资料 / 允许联网补充。只给主题且允许联网时自动搜索；明确禁止联网时不自行补充外部事实；搜索不可用时明确缺口，不使用模拟搜索冒充真实研究。

### 3.3 交付状态

- 成品：满足任务要求并通过产品内部检查；与独立业务验收分开。
- 待完善草稿：已有可用成果，但存在缺口、审校未通过或预算不足。
- 无法完成：关键资料或能力不足，不能给出有依据的答案；说明缺什么。
- 失败/取消/中断：属于执行状态，另外记录是否存在可保留的草稿与阶段产物。
- Mock 演示：始终显式标注，不计入真实搜索、真实业务质量或费用验证。

## 4. 开发思路：先实现完整功能，再整体测试优化

### 4.1 两个阶段严格分开

**D 阶段（功能开发）**：实现 G01～G15，接通入口、依赖、数据传递和失败收尾，完成可运行的全功能候选版。

**Q 阶段（整体测试与优化）**：在全功能候选版冻结后进行完整回归、真实业务评测、模式比较、质量/速度/费用调优以及试用验收。

旧文档中的“每批全量回归”“先跑真实对比再决定是否开发下一模式”“固定链优化完再扩展其余能力”“先靠模拟搜索推进试用”的排期规则由本文替代。历史实验与结果保留，不要求为了新排期重做它们。

### 4.2 D 阶段允许与不允许的工作

| 工作 | D 阶段规则 |
|---|---|
| 语法/导入、参数与契约检查 | 必要时执行，确认本步代码可以被依赖 |
| 单功能正常路径和关键失败路径 | 最小验证，可用确定性替身；记录验证范围，不能据此称整体通过 |
| 外部接口认证与一次最小往返 | 配置和预算具备时可验证功能接通；不能扩成批量质量评测 |
| 阻塞后续开发、数据损坏、越权、密钥泄露或失控调用 | 立即小范围修复，记录属于功能正确性修复，不是质量调优 |
| 单个报告分数不高、措辞不好、调用略贵、某策略暂无优势 | 登记到统一优化清单，继续完成剩余功能 |
| 全量回归、33 题批次、模式对比、提示词反复调分、吞吐压测、UI 美化 | 移到 Q 阶段，不在每批 D 开发后重复执行 |
| 运行中审校、有限修订、补搜、重规划 | 这是要开发的产品功能，照常实现；与开发人员反复优化代码不同 |

功能验证的边界：只回答“新增能力能否接通、是否遵守必需边界”；质量优化回答“能否更好、更快、更省”。不得借“验证”反复开展整体评测。也不能把明显不能运行的实现写成已完成并留给 Q 阶段补功能。

### 4.3 复用现有实现

保留现有来源/证据/产物、研究链、Runtime、SQLite、工具/技能/记忆和评测组件。先解决统一接入与数据契约；只有为本步目标所必需的结构调整才重构，不同时做目录美化和换技术栈。

根任务先于调度创建。各模式共享模型/工具网关、来源与证据命名空间、状态与产物体系。每个子任务有独立上下文和父子关系，但没有独立扩大预算、权限或改换根任务的权利。

顺序：D0 → D1 → D2 → D3 → D4 → D5 → D6 → D7 → D8 → D9 → D10 → 功能冻结 → Q1 → Q2 → Q3 → Q4。

每阶段按编号逐项完成，写明可见结果、最小验证与限制后继续下一项。下面的“完成证据”属于开发阶段的功能证明，不是整体验收。

### D0：目标、范围和状态重整

| 步骤 | 具体实施 | 完成证据 |
|---|---|---|

## 7. 功能冻结门槛：何时才能开始整体测试

进入 Q 阶段前必须同时满足：

1. D0～D10 全部必做项为“功能完成”，外部服务已具备最小真实接通证据。
2. 六种执行方式与嵌套派工均接入统一应用；Web/CLI 一致；不能只在 demo 或替身应用里运行。
3. 只给主题的联网研究路径、仅资料路径、简单工具任务、续写改稿路径均有最小功能记录。
4. 预算、权限、来源/证据和取消恢复覆盖根与子任务，已经不存在已知阻塞性断点。
5. 架构/请求/数据版本、依赖、候选代码版本或文件哈希清单、未优化问题均冻结记录。
6. 待优化清单只包含质量、效率、易用性或待整体发现的缺陷；不能把已知未实现功能挪进去。

缺搜索凭据/必要模型能力等外部条件时，可以继续开发不依赖该条件的功能；该项保持阻塞，不得先进入整体测试并声称“全功能已完成”。

### 8.1 整体验收标准

- G01～G15 全部实现且有整体入口验证；六方式和嵌套均有可运行证据。
- 冻结业务集预期行为符合率至少 90%；执行结束率、成品率、草稿率、无法完成率分别统计。
- 引用定位率 100%，人工/独立核对的语义支持率至少 95%；关键结论均有依据；伪造来源、未授权操作为 0。
- 预算、取消、恢复、审批与来源失效的必需故障案例通过；不确定调用不能被静默当作零成本或未执行。
- 需要成品的案例仍须满足正确性、结构、引用、完整性要求；能诚实拒绝不等于写作质量达标。
- 性能和成本先报告同条件基线与变化，不凭空承诺某个秒数/费用；默认参数依据 Q3 数据说明。
- Q4 试用与全新安装/备份恢复完成；无影响日常使用的未解决阻塞问题。

## 9. 记录制度、优化清单与范围控制

待优化项记入 [OPTIMIZATION_BACKLOG.md](OPTIMIZATION_BACKLOG.md)：问题、影响、证据、归属 Q 阶段和处理状态。阻塞开发的问题转为当前功能修复；非阻塞项不打断 D 阶段。

新增需求必须说明是既定目标的遗漏，还是新增范围。冻结后发现必做能力其实没有实现，要修正冻结记录并补回 D 步骤，不能伪装成调优。没有用户明确变更，不删除本计划必做能力，也不自动增加原 P2 扩展。
