## 3. 项目介绍：30 秒、2 分钟与 5 分钟版本

### 3.1 30 秒版本

> 我做了一个本地多 Agent 研究写作平台。输入资料或研究主题后，系统可以整理来源、抽取带原文定位的证据、生成报告并审校修订。我主要解决三个工程问题：子任务如何受控协作，模型每次看到什么上下文，以及交付结论是否真有证据。底层 Agent Loop 使用 LangGraph，上层补了预算、工具权限、恢复和评测。结果分成成品、草稿、无法完成和失败，避免把流程跑完当成质量达标。

### 3.2 两分钟版本

> 起点是普通大模型报告不容易核验：可能挂了引用，却不能由引用支撑结论；增加多个 Agent 后还会产生费用叠加、重复派工和恢复困难。
>
> 我将平台分成应用、编排、Harness 和模型/工具四层。CLI、Web、评测统一构造 TaskRequest；调度输出结构化执行方案，程序验证角色、依赖、并发和预算，再选择 fixed、fanout、manager_worker 等模式。
>
> 研究写作链从原始来源开始，模型提出摘录，程序要求摘录在原文中逐字可定位，再生成素材、提纲和报告。审校先做引用和章节检查，再做模型语义检查，最多有限修订，保留每个版本。
>
> 在运行治理上，根任务统一记账，子任务先预留预算、完成后结算；深度、数量、工具权限都有上限。任务状态放 SQLite，大正文放文件，恢复只复用已提交阶段，对结果未知的外部操作不自动重放。
>
> 最有价值的质量闭环是引用优化。我发现“能定位”与“能支持”不同，做了独立评审的断言—证据对判定，再通过拆分复合断言、让引用贴近支撑子句、取消缺口声明上的不当引用改进结果。12 例未见材料配对实验中严格支持率从 60.1% 到 73.4%。我会把这个结果限定为小规模实验，并说明复杂多来源材料仍有不足。

### 3.3 五分钟展开顺序

按“需求→架构→一次请求→关键难点→实验→边界”顺序讲。不要从几十个模块名讲起。

| 时间 | 重点 | 必须带的具体细节 |
|---|---|---|
| 0–40 秒 | 用户问题 | 给资料或主题，输出能核验的研究报告 |
| 40–100 秒 | 架构与请求 | TaskRequest、执行方案、根账本、共享交付通道 |
| 100–170 秒 | 多 Agent | 依赖波次并行；3 并发、12 派生、深度 2；预算预留 |
| 170–230 秒 | 可信引用 | quote 原文匹配、E 编号、来源谱系、双层审校 |
| 230–280 秒 | 实验与失败 | 19 成品+10 正确拒答=29/30 预期符合；支持率配对对照 |

## 4. 完整架构与一次请求的流转

### 4.1 责任分层

```text
CLI / Web / Eval
        |
        v
TaskRequest：任务、输入、模式、预算、权限、交付要求
        |
        v
ResearchApplication / 调度入口
        |
        v
ExecutionPlan -> 校验/预算分配 -> OrchestrationExecutor
        |                         |
        |                         +-> 子任务/并行/角色/合并
        v
研究写作链：来源 -> 证据 -> 素材 -> 提纲 -> 初稿 -> 审校 -> 有限修订
        |
        v
交付等级 + 执行状态 + artifacts / evidence / pipeline / ledger

下层共用能力：模型网关、工具执行器、Context Builder、状态库、Trace
通用 Agent 流：AgentRuntime -> LangGraph agent/tools 循环
```

这个图同时显示两条实际路径：通用 Agent 工具循环，以及阶段化研究业务链。它们共享网关和治理能力，但不能把业务链每个阶段都说成 LangGraph 节点。

### 4.2 为什么有统一 TaskRequest

入口不同不应导致同一任务有不同预算、资料或网络策略。`TaskRequest` 是不可变 dataclass，提前校验空任务、非法枚举、负数、NaN、类型和来源数量等。

子任务通过 `dataclasses.replace` 派生，保留父请求未变的字段，再显式收紧预算和权限。这比每次重新拼字典可靠：新增字段不容易在某条编排路径里丢失。

典型字段：`flow` 区分 agent/research；`orchestration` 区分协作方式；`texts/files/urls` 保存输入；`allow_network` 表示允许搜索；`required_sections` 等表达交付要求；`base_draft/revises_job` 记录改稿谱系。

### 4.3 当前预算默认值的层级

| 层级 | 示例默认 | 解释 |
|---|---|---|
| 应用 TaskRequest | 40 次调用、累计 65536 输出 token、600 秒、估算 $0.15 | 整个根任务的护栏，研究链当前入口口径 |
| Agent RuntimeContext | `max_iterations=5`、`context_budget=12000` | 通用 Agent 循环与上下文配置；与应用默认不是同一个维度 |
| 执行方案 | 单层并发≤3、派生总数≤12、嵌套深度≤2 | 子任务扩展约束 |
| 模型单次输出上限 | 由配置/Adapter 决定 | 不要与“累计输出 token”混淆 |

在面试里看到不同数字，先回答它属于哪层，再解释它如何被上层根预算限制。不要把 `compose_context` 函数参数默认 6000 与当前 RuntimeContext 12000 混为一谈。

### 4.4 一次资料研究请求的具体过程

1. 解析任务和输入，生成 job_id，落请求快照与根账本。
2. 导入资料：保存正文副本、来源元数据、解析状态和定位信息。
3. 若允许自动联网且搜索配置有效，规划有界查询，读取候选正文，登记来源；指定 URL 导入与自动搜索是不同授权场景。
4. 请求 auto 模式时，调度器生成方案，程序验证枚举、依赖和预算。结构化输出失败按规定降级，保留原因。
5. 若并行拆题，按依赖波次启动子任务。每个子任务先预留预算，结果回到根任务；原始来源和子产出谱系需要一并保留。
6. 最终报告通过共同研究链生成，不能直接把子 Agent 文本拼起来就宣布成品。
7. 程序与模型审校，有限修订，记录问题、硬要求检查和交付等级。
8. 写入版本化产物与状态。工作台读取这些产物，不以临时 UI 文本为权威。

### 4.5 Job、Run、Thread 的区别

- **Job**：用户业务任务，是统一预算、输入来源和交付的单位；可以包含多个子任务和模型调用。
- **Run**：一次 Agent 运行，主要对应 runtime 的 `run.json/trace.jsonl/usage.json`。
- **Thread**：LangGraph 会话键，连接多次调用的图状态，不代表一个线程池工作线程。

例子：一项研究 Job 拆成三个子 Job，每个子任务可以调用一个或多个 Run；只有显式使用相同 thread_id 与同一 checkpointer 时，会话状态才会关联。

## 5. LangGraph、Agent Loop 与状态管理

### 5.1 四个核心概念

State 是运行状态快照；Node 读取状态并返回更新；Edge 决定下一步；Reducer 决定字段如何合并更新。`compile()` 产生可执行图。

项目的 `AgentState` 把流程字段与执行流分开：iteration/max_iterations 控制循环，messages 保存对话，tool_events/errors 等用于累积。静态配置放 RuntimeContext，大正文和正式产物放 Workspace。

这样的好处是：运行控制不依赖从自然语言对话里猜状态；恢复、调试和测试可以检查明确字段。

### 5.2 Agent Loop 的实际路由

```text
START -> agent
          | 无 tool_calls -> END
          | 有 tool_calls 且未到上限 -> tools -> agent
          | 有 tool_calls 且达到上限 -> timeout -> END
```

agent 节点组装上下文、调用模型、增加 iteration、记录用量并检查预算。tools 节点只处理当前最后一轮 assistant 的工具请求，执行后回填 role=tool 消息。`tool_call_id` 必须对应请求 ID，否则模型无法可靠关联结果。

iteration 主要是模型轮次数，不是 Python 函数执行次数。Graph 自身的递归限制与业务的 max_iterations 是不同防线。

### 5.3 Tool Calling 与 ReAct

Tool Calling 让模型输出结构化工具名和参数；实际执行仍由程序完成。ReAct 是交替利用观察结果选择动作的思路，可以用 tool calling 实现，但不要求打印模型内部思维。

在这个项目里，trace 可记录角色、工具、阶段、终止原因和用量；这些是外显执行轨迹。不要宣称保存了所有模型隐藏推理过程。

### 5.4 Reducer 为什么重要

项目使用 `Annotated[list, operator.add]` 追加消息和事件。节点返回 `{"messages": [new_message]}`，应与已有消息合并，而不是覆盖历史。

需要知道两点：

1. 普通字段通常按更新值覆盖；多个并行节点写同一字段需要定义合并规则。
2. 本项目的 append reducer 不具备官方 `add_messages` 按消息 ID 更新的全部语义。重复写同一消息可能重复追加，不能说两者完全等价。

如果以后在同一图内并行写证据，应该按稳定 ID 合并并检测冲突，而不是盲目追加。上层线程池并发结果通过主线程汇总，与 LangGraph 图内 reducer 合并也要区分。

### 5.5 Checkpointer 的真实范围

`make_checkpointer()` 当前返回 `MemorySaver`。同一个 Runtime 实例、同一个 thread_id 可以保持图会话状态；进程结束后内存 checkpoint 不会自动保留。

项目的跨进程研究恢复依靠 SQLite 状态和 `stage_*.json`，不依靠 MemorySaver 的磁盘持久化。只说“用了 LangGraph checkpoint，所以进程重启后自动恢复全部任务”会与当前代码不符。

术语核对可参考 [LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)，具体后端以本项目 `memory/checkpointer.py` 为准。

### 5.6 为什么上层还需要 Harness

图运行框架不会自动决定：哪些内容可以进模型、子 Agent 是否能获得父权限、工具超时后能否重试、如何估算费用、结构正确的报告是否事实正确。

项目的 Harness 负责这些运行约束。可用一句话回答：“LangGraph 负责状态和执行路由，Harness 负责上下文、工具、预算、生命周期与运行观测；业务层负责研究结果如何验收。”

## 6. 多 Agent 调度、依赖图、并发与 EventBus

### 6.1 多个 Agent 在这里是什么

通常是不同角色配置、任务上下文、工具集合和运行身份，不是六个独立训练模型，也不是六个独立服务。多个角色可以共享同一个模型 Adapter。

角色由 researcher/organizer/writer/editor/agent 等配置表示。角色提示词解决职责分工，真正的隔离还要靠输入边界、工具权限和预算。

### 6.2 六种模式

| 模式 | 适合什么 | 收益 | 代价与风险 |
|---|---|---|---|
| single | 简单任务、低预算 | 减少协作开销 | 不能把单个 Agent 等同于一次模型调用 |
| fixed | 稳定研究写作流程 | 容易控制阶段和恢复 | 复杂主题可能拆解不足 |
| fanout | 相互独立的多个子主题 | 并行减少等待 | 合并、去重、来源回溯更难 |
| manager_worker | 先规划再派工 | 统一组织子任务 | Manager 规划错误影响全局 |
| dynamic_team | 任务结构和角色需动态决定 | 根据依赖组队和推进 | 验证、重规划、预算开销更高 |
| debate | 存在分歧或关键决策 | 对照支持/反对证据 | 同模型偏差相关，Judge 仍可能错误 |

fixed 是应用侧的执行方式名，底层顺序策略模块使用 pipeline 命名。不要把模块名差异当成两套完全无关功能。

### 6.3 调度输出必须是契约

ExecutionPlan 包括 mode、reason、subtasks、depends_on、max_parallel、budget、fallback_mode 等。模型建议不直接执行，必须验证：

- mode 和 role 属于开放集合；
- 子任务 ID 唯一，描述非空，数量不超上限；
- 依赖存在，不依赖自身，不构成循环；
- 并发符合上限，预算为有限非负值；
- 子任务对必需章节的覆盖与汇总要求一致。

契约校验失败时修正或降级，而不是猜测模型自创字段是什么意思。计划预算取用户/系统上限的较小值，模型不能自己把预算放大。

### 6.4 DAG、拓扑顺序与依赖波次

假设 A=研究技术，B=研究成本，C=研究风险，D=综合推荐，依赖关系为 A/B/C→D。

A、B、C 可以同一波执行；D 必须等到前置成功或明确处理缺口之后执行。依赖图不是“所有节点一起丢进线程池”。

ready 集合条件：任务未完成，且前置条件已满足。若 pending 非空但 ready 为空，可能是循环、依赖失败或非法计划，必须有明确终止/重规划出口。

### 6.5 Python 并发怎么实现

线程池限制同时执行数，Future 保存结果或异常。子任务提交时使用 `copy_context().run`，使父调用的 ContextVar 账本、角色等上下文进入工作线程；每次提交使用独立上下文副本。

结果按计划顺序收集，输出顺序不会因为完成先后而随机变化。多线程适合模型 HTTP 等 I/O 等待；不要泛化成“Python 线程让所有 CPU 计算获得三倍加速”。

等待超时或取消 Future 不能撤销已经运行的函数，这是后续工具超时和副作用治理的关键。参考 [Python concurrent.futures](https://docs.python.org/3/library/concurrent.futures.html)。

### 6.6 为什么并发 3 不等于整链快三倍

对独立等时任务：串行近似 `N×t`，并行近似 `ceil(N/P)×t + 调度开销`。N=6、P=3 时理想是两波，耗时约变成三分之一。

实际研究还包含串行调度、资料抓取、合并、成稿、审校，且有长尾和服务端限速。若可并行部分占比 f，理想整体加速可用 `1/((1-f)+f/P)` 作上限分析。f=0.6、P=3 时只有约 1.67 倍，即耗时约少 40%。

这个分析解释为什么 66.5% 只能限定为离线可并行部分实验。

### 6.7 如何防止无限派工

执行方案和工具派工分别有数量、深度、重复任务、迭代与预算限制。子任务权限取父允许集合与子角色/技能集合的交集，不能把父任务未有的权限凭角色名获得。

“工具叫 delegate_subagent”不意味着它可以无限递归。深度到 2、派生到 12、预算不足或连续失败熔断时，必须拒绝继续扩展。

### 6.8 EventBus 的实现与限制

总线提供 publish/subscribe/unsubscribe/replay。锁保护订阅表、seq 和历史 deque；发布时复制 handlers 后在锁外同步回调；单个订阅者抛异常不会阻断其他订阅者。

seq 是单调编号，但多个线程的 handler 执行时间可能交叉，所以不要承诺跨线程回调的全局严格顺序。历史最多保存最近 500 条，不是永久不丢的日志。回调是同步执行，慢订阅者仍会拖慢发布方。

`tracer_bridge` 把事件转成 Trace。工作台依靠服务接口和产物读取，当前不能描述为所有 UI 更新均通过 EventBus。它是进程内组件，不是 Kafka，也不提供分布式投递、持久化重放或 exactly-once。

## 7. Skill 生命周期、依赖解析与渐进加载

### 7.1 Skill、Tool、Agent、知识的区别

| 对象 | 作用 | 例子 |
|---|---|---|
| Agent | 在上下文和约束内决定下一步 | 研究员决定需要哪些证据 |
| Tool | 执行一个程序能力 | 计算、读取来源、MCP 工具 |
| Skill | 可复用任务方法与约束 | 来源审计、风险分析的步骤说明 |
| Knowledge/Source | 提供事实材料 | 领域文档、导入网页 |

Skill 告诉模型“怎么做”，工具执行“具体动作”，资料回答“依据是什么”。把所有 Skill 都包装成工具函数没有必要。

### 7.2 技能文件与发现

注册表扫描技能 Markdown，解析 name/description、allowed_tools、depends、references 等元信息，记录不合法文件的诊断。`reload()` 是显式重新扫描，不等于后台监听文件每次变化。

description 必须能区分用途。过长会消耗路由上下文，过宽会误召回。技能还需要清楚的输入、输出和适用条件，而不是一段泛泛的角色设定。

### 7.3 生命周期

```text
discovered -> activated -> running
                  ^          |
                  +----------+ end_run
activated/running -> deactivated -> activated
```

激活前解析依赖；begin_run 标记本轮生效；end_run 收回到 activated；deactivate 标记停用。任务异常也通过 finally 清理，避免技能永久停在 running。

四态不是一个一次性线性流程。activated 可以幂等激活，deactivated 可以再次启用。状态为 running 并不代表启动了外部进程。

### 7.4 依赖解析算法

用 DFS：path 表示当前递归路径，seen 表示已经处理的节点。依赖先访问，自身最后；缺文件直接报缺失，遇到 path 中已有节点报告循环。

如 A depends B、B depends C，激活顺序 C→B→A。复杂度在图规模上约为 O(V+E)。依赖不是由模型自行猜测，而是文件显式声明。

需要注意：依赖“已激活”与依赖“正文一定注入当前 prompt”不是同一事实。当前 Runtime 注入选中技能正文；若面试官问依赖内容如何组合，应按源码回答，不能承诺完整技能包自动组合执行。

### 7.5 两级路由与三级加载

路由：BM25 先召回候选，真实模式可用模型选择；离线或 rerank 失败时用召回结果兜底。路由器支持 NO_SKILL，一次选择一个主技能。

加载：

1. metadata：名称和说明，用于选择；
2. fullcontent：命中技能的完整指令；
3. references：较大辅助资料，通过已声明引用按需读取。

三级加载是 API 能力；81.6% 的实验只覆盖“所有元信息+一个命中全文”，未计额外 references 和依赖全文。多命中或长参考资料会减少节省幅度。

### 7.6 为什么节省 token 不等于效果一定提高

无关内容减少可以让任务更清晰，但误路由会漏掉方法，缺依赖内容会造成执行不完整。需要同时测路由命中、任务质量、失败率和上下文用量。

面试回答：“渐进加载解决上下文扩展问题，实验验证的是内容注入开销；任务质量仍需要另行评测，不能只优化 token 数。”

## 8. 三层记忆、向量检索、BM25 与遗忘衰减

### 8.1 三层记忆的语义

| 层 | 存什么 | 生命周期 | 当前实现 |
|---|---|---|---|
| Working | 当前会话临时材料 | 会话内，有界 | 线程安全 deque，默认 50 条 |
| Episodic | 历史任务经历、成功失败经验 | 跨会话，可过时 | LongTermStore+索引，低可检索度可删除 |
| Semantic | 可复用知识、偏好、事实 | 跨会话 | LongTermStore+索引，衰减降权而不按遗忘阈值删除 |

LongTermStore 还定义 procedural 类型；三层门面突出 working/episodic/semantic，并不代表底层完全没有程序性经验记录。

记忆不是证据权威。报告里的事实仍需回到当前可核验来源，不能把历史模型结论当原始来源引用。

### 8.2 当前默认链路与三层组件的差别

这是本次核查必须牢记的事实：默认 AgentRuntime 实例化 `LongTermStore(workspaces/memory_store.json)`，使用它的 `search(task, top_k=3)`；该实现不是三层向量+BM25 路径。

`MemoryLayers` 构造索引并提供分层查询，`LayeredMemoryProvider` 将结果渲染成可注入块，已在组件测试与 resume_metrics 中使用。不能把它们描述成默认 AgentRuntime 已经完全使用的记忆后端。

SQLite 状态库、SQLite 向量索引和 JSON 长期记忆是不同存储职责。也不要说“所有记忆都持久化在 SQLite”。

### 8.3 哈希嵌入的具体步骤

`embed()` 默认 256 维：中文按双字词等口径切词，英文按词；每个 token 用稳定 FNV-1a 哈希映射到一个维度；累加频次；最后 L2 归一化。

相比 Python 内置 hash，稳定哈希能保证跨进程生成同一向量。它无需外部模型调用，易于离线测试。

局限：不同词可能发生哈希碰撞，改述如果缺少词面重叠可能检索不到，跨语言语义对应较弱。sqlite-vec 负责向量存取和搜索，不会把哈希向量变成神经语义嵌入。

如果问“为什么不是 BGE/Qwen embedding”，回答当前目标是低依赖、可复现的小规模组件，神经 embedding 属于后续可替换方案，不宣称已经使用。

### 8.4 sqlite-vec 与类名 sqlite_vss

`SqliteVssIndex` 类和 backend 标签保留 `sqlite_vss` 名字，但源码导入 `sqlite_vec`，创建 `USING vec0` 的虚拟表。准确技术名是 sqlite-vec。依赖不可用时 `auto` 回退 `HashingVectorIndex`，显式指定 sqlite_vss 时失败报错。

历史报告显示当时实验用了 sqlite_vss 标签后端；本次没有为证明历史数字去安装扩展，也没有声称当前所有环境都启用该后端。

项目官方技术入口：[sqlite-vec](https://alexgarcia.xyz/sqlite-vec/)。

### 8.5 余弦与 L2 的公式

单位向量 x、y 满足 `||x-y||² = ||x||²+||y||²-2x·y = 2-2cos(x,y)`，所以：

```text
cos(x,y) = 1 - L2_distance² / 2
```

当前 sqlite-vec 返回距离后按这个关系转分数。前提是两向量都单位归一化；空文本生成的零向量不满足单位向量条件，不能把公式不加条件推广到所有输入。

索引返回大分数好、小距离好。如果两后端分数尺度不一致，混合重排会失真，这也是需要后端一致性测试的原因。

### 8.6 BM25 与混合重排

BM25 同时考虑词频、词在语料中的稀有程度和文档长度，避免“任务、预算”等高频域词支配结果。项目用 k1=1.5、b=0.75，在候选集内计算 IDF，并将词面分归一化。

```text
BM25(D,Q) = Σ IDF(t) * tf(t,D)*(k1+1)
                       / [tf(t,D)+k1*(1-b+b*|D|/avgdl)]

最终分 = (向量余弦 + 0.5 * 归一化 BM25) * 可检索度
```

流程：向量先召回 top_k×5，再解析 MemoryRecord、BM25 重排和衰减，最后取 top_k。

局限：BM25 只在向量候选内重排，词面很准但向量未召回的记录仍可能丢失；这与“双路独立召回后融合”不同。若要改进，可考虑词面和向量候选取并集，再用 RRF 或校准分数融合，但这不是当前已实现事实。

### 8.7 遗忘衰减

```text
retrievability = exp(-间隔天数 / stability)
```

刚访问时约为 1；间隔越大越低；stability 越大下降越慢。命中记录强化 stability，并更新访问时间，上限限制其无限增长。低于阈值的 episodic 可以物理清理，semantic 保留但降权。

这是工程启发式，不是对人类记忆的严格建模。stability 不是事实可信度，confidence 也不能因为频繁被检索就变成事实真值。

还有一个副作用：反复检索同一错记忆会强化它，因此需要来源、失效标记、更正和写入策略，而不应无限自动记住模型输出。

### 8.8 Top-3 命中率与召回率的区别

实验一条 query 对应一个指定正确记忆 ID；正确 ID 在前三即命中。`Hit@3=74/100`。它不是多相关文档的 `Recall@3=相关结果召回数/全部相关结果数`，也不是最终答案正确率。

Bootstrap 重采样 2000 次给出约 65%–82% 的 95% 区间。它反映这 100 条查询样本的不确定性，不消除人工构造查询偏差，也不证明生产表现。

## 9. Context Engineering 与提示前缀稳定性

### 9.1 Prompt、Context、Harness Engineering

Prompt Engineering 关注如何表达任务和约束；Context Engineering 关注本次调用提供哪些内容、顺序、角色和预算；Harness Engineering 关注模型运行周围的工具、权限、状态、预算、恢复与观测。

以这个项目为例：引用纪律提示词是 Prompt；按需 Skill、记忆和证据限窗是 Context；任务账本、工具审批和阶段恢复是 Harness。

### 9.2 ContextSource 与可见性

每类上下文有 kind、content、policy。PRIVATE/NEVER_EXPOSE 不进入模型；SUMMARY_ONLY 做摘要；相关检索结果应由调用方先筛选，再进入组装。

“RETRIEVE_IF_RELEVANT”标签不是自动语义鉴别器，更不是安全沙箱。源选择、相关性和信任等级仍需要上层负责。

### 9.3 预算分配

默认权重：instructions 10%、task 10%、messages 20%、evidence 30%、memory 10%、tools 10%、reserve 10%。这些是策略，不是模型最大上下文长度的严格 token 校验。

当前 token 估算按中文字符与其他字符启发式计算，并不等于模型 tokenizer。基础 system、不同 kind、工具消息及特殊标记也可能影响实际长度，因此不要声称上下文永不超过模型限制。

需要防止一份大素材包挤掉全部历史，也需要防止历史挤掉当前证据。O-15 曾出现历史窗口恒两条、恢复份额后大素材包又被截断的问题，说明预算必须按任务实际输入校准。

### 9.4 记忆为什么可以放在用户消息

静态系统规则、角色和输出格式尽量在前；变化的证据、记忆、任务在后。若动态记忆插在历史之前，相邻请求会较早发生变化，减少可复用前缀。

项目支持 `user_message_kinds`，将 memory/evidence/handoff 放入带 `<<CONTEXT>>` 标记的 user 内容；标记也帮助模型网关避免重复组装。

但“放进 user”本身不保证缓存命中：历史修剪、技能变动、工具 schema、角色配置和请求序列化都可能改变前缀；不同服务商缓存规则也不同。

### 9.5 29pp 的准确表述

实验逐轮比较相邻 messages：从前向后，只要 role/content 完整一致，就累计该消息的估算 token；遇到第一条不同消息就停止。它没有逐 token 检测两条不同文本的共同子串，也没有请求供应商缓存统计。

```text
稳定前缀占比 = 开头连续相同消息的估算 token / 当前消息总估算 token
```

保存结果在历史窗口修复对照下为 system 注入 42.42%、user 注入 71.33%，差 28.91 个百分点。可以讲“代理指标改善”，不能讲“实际费用节省 29%”或“实际命中率提升 29%”。

### 9.6 当前开关事实

`memory_in_user_message=False`，`reserve_message_window=True`。前者表示默认仍未切入用户消息；后者表示默认启用历史预算份额修复。它们是两个开关。

旧记录将它们合并成“已默认兑现”有误。面试可回答：“机制已经实现并做过对照，默认 AgentRuntime 的记忆位置仍由开关决定；这部分需要区分实验配置与默认配置。”

### 9.7 工具消息的完整性

裁历史时，不能只保留 tool 结果而丢掉对应 assistant.tool_calls，或者只保留请求不保留结果。这会破坏消息协议和模型理解。项目对已组装消息和工具续轮有绕过重复组装的分支；它是需要结合测试理解的边界，不代表任意复杂历史都已被完美处理。

## 10. 来源、证据、引用谱系与研究写作链

### 10.1 三个层级

**Source** 是原始资料及登记信息；**Evidence** 是从资料摘取、可定位的证据记录；**Claim** 是最终报告断言。

```text
报告断言 [E-001]
       -> evidence_id / fact / tag / quote / source_id / locator
       -> sources.json 中的来源身份与版本
       -> 来源正文、段落或 PDF 页码
```

“模型说这是事实”只属于 fact 字段的提议，必须检查 quote 与来源、claim 与 quote 的关系。

### 10.2 资料导入与去重

当前处理粘贴文本、TXT/Markdown、文本型 PDF、指定网页。扫描 PDF 不自动 OCR；图片和表格复杂布局不是已完备支持的能力。

来源记录保留状态：ok/partial/duplicate/empty/unsupported/too_large/read_failed 等。内容哈希和归一化哈希支持重复检测；不同来源同事实不是直接判重复，不同指标差异也不是直接判冲突。

典型限制是单任务最多 20 来源，单来源 2MB，累计来源正文 10MB；下载限制与正文存储限制是不同层。超限要有明确结果，不能假装读取了全部。

### 10.3 证据抽取的程序校验

模型生成 fact/tag/quote。程序检查 tag 在 F/I/U 内、fact 非空、quote 非空且长度≤400、quote 在来源正文逐字存在；失败条目不入证据库，并记录 issue。

找到 quote 的偏移后映射段落，PDF 提取的页码信息进入定位。E 编号是任务内稳定身份，修订不应让旧引用偷偷指向新内容。

单来源供模型抽取的正文有字符预算，当前代码上限 40000 字符，截断会说明后段未提供。它不是无限长文全覆盖。

`str.find` 找到的是首次匹配；重复句、多位置相同 quote 或标准化差异是后续可能细化的边界。不能把“逐字存在”说成“准确理解上下文”。

### 10.4 F/I/U 与最终报告标签

- F：材料明确表达的事实提取；
- I：推断，应明确依据和条件；
- U：未知或缺口，不得编造为事实。

报告使用事实/推断/未知标记，以便审校和用户判断。这些标签本身不是正确性证明，模型仍可能误标，需要支持关系审核。

### 10.5 为什么多 Agent 还要引用谱系

子 Agent 可能将原始材料总结成文本，根任务再将其当“新来源”抽取。如果只引用子报告，用户会看到循环引用，无法证明原始事实来自哪里。

项目通过原始 source_id、root_source_id、source_version、source_job_id 等谱系信息回补，最终核验应能沿证据回原始资料。子产出可以作为中间材料，但不应替代原始依据。

### 10.6 研究链各阶段做什么

| 阶段 | 输入 | 输出 | 必须防的错误 |
|---|---|---|---|
| evidence | 来源正文 | 原文定位证据 | 伪造摘录、错来源 |
| material | 证据与任务 | 素材、主题、冲突与缺口 | 忽略缺口、误判冲突 |
| outline | 素材与交付要求 | 标题、章节、需要的证据 | 自造结构替代用户要求 |
| draft | 提纲与证据 | 报告初稿 | 推断当事实、引用跨范围 |
| review | 初稿与结构/证据 | 程序检查+语义问题 | 只有格式通过便接受 |
| revision | 问题清单与上一稿 | 新版本 | 覆盖历史、无限自改 |
| delivery | 审校状态与任务覆盖 | 等级、产物、局限 | 把草稿伪装成品 |

当前默认最多自动修订两轮。超过轮次仍未满足要求，交付草稿或无法完成，而不是继续无限消耗预算。

### 10.7 三种交付类型

collection：整理资料与素材；analysis：短分析；report：结构报告。流程不能只对 report 做质量检查而放任短分析直接判 accepted，O-19 的修复正是补短交付审校。

改稿使用原稿文本和修改要求，保留旧版与变更说明。source_update/revises_job 记录来源变更和任务继承，避免用户追问后丢失原资料。

### 10.8 可定位、支持、真实、完整的区别

| 维度 | 检查的问题 | 不能推出什么 |
|---|---|---|
| 可定位 | 引用能否找到来源摘录 | 摘录一定支持结论 |
| 语义支持 | 摘录是否支撑断言 | 原始来源一定真实可靠 |
| 来源可信 | 材料发布者、方法和时效是否可信 | 报告已经回答所有问题 |
| 任务完整 | 是否覆盖用户目标及必要条件 | 所有结论均有充分证据 |

例如材料写“40 名试点参与者中 30 人满意”，报告写“全国用户满意度为 75%”。引用完全可定位，但结论把试点范围扩大到全国，语义支持不成立。

即便报告准确引用一份低质量来源，也可能只做到“忠实复述不可靠信息”。面试时应承认来源质量不是引用格式能解决的。

## 11. 双层审校、拒答与四级交付

### 11.1 程序层与模型层

程序层适合确定性条件：引用 ID 存在、要求章节出现、必要证据覆盖、标记格式和字面命中。模型层适合语义支持、事实冲突、任务遗漏与表达。

模型输出“accepted”不能覆盖程序 error。反过来，程序没有 error 也不意味着业务一定好，还要看模型审校、交付封顶与独立评测。

### 11.2 禁用表述当前是 warn

这点与 README 的一些历史描述不同。`hard_requirement_issues()` 当前对必需章节缺失判 error，对 forbidden_claims 字面命中判 warn，对 key_facts 字面缺失判 warn。

原因之一是否定句也包含禁语：报告写“不能断言全国满意度为 75%”，不能因为包含禁止短语就判它做了错误断言。当前策略保留疑似命中，交给语义评测/人工复核。

风险是单靠字面 warn 不能提供强制内容合规保证。简历可以写“程序层校验并记录禁语疑似命中”，不要说所有禁语一出现必然拦截。

### 11.3 四个交付等级与四个执行状态

| 交付等级 | 意义 | 示例 |
|---|---|---|
| accepted | 链内成品判定 | 本轮结构和审校通过 |
| draft | 可用草稿但仍需完善 | 未修完关键问题或覆盖不足 |
| unable | 当前证据无法完成目标 | 缺核心事实，诚实拒答 |
| failed | 链阶段出错，未形成正常交付 | JSON 持续失败、执行异常 |

执行状态另有 completed/partial/failed/cancelled。unable 通常映射 partial，而不是把“诚实拒答”当作业务成品。异常、预算取消和证据不足也应分别记录终止原因。

### 11.4 拒答机制的入口

零可用证据可以确定性返回 unable；提纲阶段支持 cannot_answer；报告自述检查 `delivery_cap` 防止正文承认核心目标无法覆盖却标 accepted。

但有条件推荐与完全拒答要区分。若已有材料足够形成限定条件下建议，应给出建议、假设和缺口，而不是一律“证据不全就不能做”。若核心问题没有依据，不应凭空给确定答案。

### 11.5 accepted 为什么还需要独立评测

链内审校属于生产路径，有预算和上下文局限，也可能与写作模型共享偏差。独立评测依据外部参考和评分规则另判，不受链内 accepted 的结论约束。

项目历史 Q2 的“流程完成 97%”“行为符合 70.8%”“accepted 子集独立质量 61.3%”就是三者分离的实例。不能挑最高一个数字称总体成功率。

### 12.2 耗时降低与加速比

```text
耗时降低 = (串行耗时 - 并行耗时) / 串行耗时
加速比   = 串行耗时 / 并行耗时

0.902 -> 0.302:
耗时降低 ≈ 66.5%；加速比 ≈ 2.99x
```

不能说“加速比为 66.5%”。报告主指标按各轮 reduction 的平均值汇总，展示均值再算可能有四舍五入差异。

保存的原始报告是 50 轮，旧文档某些段落写 20 或 100 轮，不能把不同运行描述混在一起。后续若复现实验，可以跑更多轮，但新的次数不能追溯替代历史报告。

### 12.3 技能估算 token

```text
节省率 = 1 - 渐进注入估算 token / 全量全文注入估算 token
约为 1 - 1073/5819 = 81.6%
```

逐个技能作一次主命中，得到 17 个结果，区间 78.7%–84.8%。5819/1073 是技能构造文本的口径，不包括用户问题、历史对话、工具 schema、其他系统规则、生成输出和路由模型自身的开销。

如果问“有没有用真实 tokenizer”，回答没有，这个数字来自 `estimate_tokens`；若要供应商成本结论，还需记录实际 usage 并保证效果可比。

### 12.4 记忆实验的边界与文档冲突

历史报告：100 查询，Top-1=60%，Top-3=74%，bootstrap 2000 次，95% 区间约 65%–82%。当前脚本 `REUSE_CASES` 为 100 条，写入这些知识后查询；目标知识之间也互为候选干扰。

旧 `RESUME_PARITY_PLAN` 写了额外 100 条干扰知识，但当前脚本没有单独写入干扰集，历史 JSON 也没有干扰数量字段。本次不能证明该额外规模，不要在面试里引用为确定事实。

跨会话组件复用不等于跨进程恢复：实验写入“session_A”来源标记，再查询同一层对象，并未单独证明重启后索引重建、JSON/SQLite 一致恢复和完整 Provider 接入。

### 12.5 96.7% 与报告成品率

v3 纪律版：20 个有答案任务中 19 成品、1 草稿；10 个无答案任务均无法完成且诚实拒答。

```text
预期行为符合 = (19 成品 + 10 正确拒答) / 30 = 96.7%
全任务成品比例 = 19/30 = 63.3%
有答案子集成品比例 = 19/20 = 95.0%
```

三者都可以有意义，但含义不同。`business_report.totals.passed=19` 的脚本只将 accepted 算 passed，所以其中 failed=11 包含 10 个正确拒答；不能把 failed=11 全解释为系统错误。

### 12.6 引用支持率的两套口径

评审标签 supported/partial/unsupported/unrelated。

```text
strict  = supported / 已完成判定的对数
lenient = (supported + partial) / 已完成判定的对数
```

原始混合集：359 supported、102 partial、56 unsupported、27 unrelated，分母 544。纪律版 v3：228 supported、20 partial、9 unsupported，分母 257。

**不能直接写 66.0%→88.7% 为严格控制变量收益。**两边案例范围不同。按当前缓存将旧数据限制 case_id 以 pc/pu 开头：296 supported、71 partial、39 unsupported、20 unrelated，分母 426，严格 69.4836%，宽 86.1502%。

因此当前可复核的 v3 同案例范围对照是：**69.5%→88.7%，+19.2 个百分点**。旧日志中约 69.1%、444 对与当前经过过滤的缓存不同，本文保留差异，不倒改原始报告，也不声称完全重现当时每一次解析口径。

如果面试只需要最稳的改进结果，使用留出集 **60.1%→73.4%**，并说明样本少与输出分母变化。

| 英文 HotpotQA 6 例 | 114/180=63.3% | 77/112=68.8% | +5.4pp，四舍五入口径约 +5.5pp |
| 合计 12 例 | 203/338=60.1% | 138/188=73.4% | +13.3pp |

同题配对指同一任务在旧/新规则下分别运行，不代表旧新输出的每一条引用对一一相同。两组整体提升，但 pd05、pd06、ph01、ph04 等个别题严格支持比例下降，不能说“每题均提升”或“完全无退化”。

少引、精确引减少了对数，也可能改变覆盖。仅看支持比例不够，还要核查必要事实覆盖、输出长度、拒答和任务完成情况。

### 12.8 85% 一致率怎样解释

17/20 是观察一致率，样本少。它不等于 85% 的全体标签准确率，也不等于有 85% 报告正确。分层抽样与过滤前后标签是否一致，会影响解释。

需要准备：20 对如何选、标注者是谁、是否先独立判再看模型、分类标准、3 个分歧如何裁决、原始表在哪里。本次只有日志记载，未发现独立标注表；不能代替你确认曾经做过人工标注。

真正建立人工校准时，应记录 claim/quote、模型标签、盲标人工标签、理由、裁决和版本。需要多标注者时可增加 Cohen's kappa 等一致性统计，但目前不能宣称已经具备。

### 12.9 958 的确切分母

`q2_real_batch/business_report.json` 的 99 条记录 `machine_checks.citation_tokens` 总和为 958，`unresolved_citations` 总和为 0；`q2_rescore_graded.json` 同样可以重算。

accepted 子集有 80 条记录，其中引用标记共 710。958 不是 accepted 子集，也不是 958 个去重证据、958 个来源或 958 个独立事实。解析器能识别的标记格式之外，不能因未计入分母就推定全部正确。

### 12.10 指标回答的通用六件套

讲一个数字时，必须能补充：**数据集、样本量、运行模式、对照条件、分子分母、局限**。多 Agent 提速还要说是否计成稿/审校；支持率还要说判定模型与过滤规则；缓存还要说是否来自真实 usage。

## 13. 全链路评测、独立评审与人工复核

### 13.1 为什么分三层

单元/组件验证证明机制按约定运行；离线业务桩证明流程和契约；真实模型任务证明当前配置在选定案例上的实际行为。三层不能互相替代。

Mock First 的价值是成本低、可控制故障、容易复现；限制是规则桩不会暴露真实模型的语义错误、输出格式漂移、网络限速和推理 token 消耗。

### 13.2 三分离指标

执行完成率：尝试是否真正执行结束，有没有未执行或运行故障；预期行为符合率：交付是否符合任务期望，例如该拒答时拒答；成品质量率：被判成品的结果独立复核是否达标。

历史 Q2：96/99≈97.0%；68/96≈70.8%；49/80≈61.3% 为 accepted 子集独立评审通过；对应人工口径另有 57/80≈71.3%。不能把人工全部样本的 65/94≈69.1% 与 accepted 子集的 71.3% 混用。

旧重算报告还保留“参考关键事实曾注入任务”的提示效应 caveat，说明重算统计本身不能消除旧运行见过提示的影响；不能凭“closed”文件名就为所有历史批次背书严格盲测。

### 13.3 公开数据转换做了什么

MRC 原题通常短问短答，研究平台输出结构报告，不能直接套用原榜单分数。因此转换为 sources+task+sections+facts+expected_outcome 的业务案例。

v3 使用 CMRC 20 例和 DuReader 无答案 10 例；v3b 使用 DuReader train 有答案 6 例和 HotpotQA distractor validation 6 例。Hotpot 每题多段材料含干扰，作为多来源压力测试。

脚本使用确定 seed，保留 raw_id 与来源映射，断言 quote 在提供材料中逐字存在。42 例是工程验证集，不是完整公开数据集评测，也不能声称达到公开排行榜结果。

### 13.4 “闭卷”在这个项目里的含义

指执行者只使用提供资料，禁止借外部检索或参考答案完成；不是把资料也不给模型。正确答案/评分事实应在评测端保留，不作为用户任务隐藏提示传给生成模型。

要核查运行实际请求快照、联网开关、事实注入参数，不能只看数据文件。评测脚本支持某种配置，也不证明每个历史批次都用了该配置。

### 13.5 LLM-as-a-Judge 与链内 Reviewer

Reviewer 在业务链内给修订意见；Grader 是运行后按独立标准打分；support_rate 的 Judge 是逐对判断引用支持。三个角色不是同一个指标。

整体评审四维：正确性、结构、引用、完整性；时延和费用走程序指标。不同模型评审有助于减少同模型自评偏差，但同模型家族仍可能相关，模型判分仍需人工抽检。

### 13.6 支持关系判分流程

报告解析成带引用单元，回溯 evidence.json，把 unit 与 quote/fact 一起提交独立判定模型，默认 8 对一批。缓存按对身份复用，未完成判定单列；缺失证据不能静默消失。

纯引用簇、簿记行会被过滤以免污染分母。过滤规则应该可复核，短事实不能因字数少被误丢。判定缓存可降低重复费用，但文本、规则或 Judge 版本变化后要核查缓存是否仍适用。

目前测的是**已带引用的断言支持比例**。没引用的事实断言可能不入 pair 集，因此高支持率不等于全报告所有事实都有依据。还要有无引用断言检测或人工覆盖检查。

### 13.7 一句多引为什么容易判 partial

如“方案 A 更便宜且更稳定 [E-001][E-002]”：E-001 只有价格，E-002 只有稳定性。若对整个句子分别评价每条证据，两条都只支持一部分。

改为“方案 A 成本更低 [E-001]；在给定测试条件下故障率更低 [E-002]。”能让引用范围准确。但拆句不能删除必要限定词，也不能只为提高分数删除难回答内容。

### 13.8 人工复核的实际层次

项目有人类评分表导入和 human_confirmed 字段。用户确认采用 AI 预填分，与完全独立盲标人工评分不同。应说明实际过程，不能因为字段为 true 就声称全部人工原创判断。

Q4 试用有正式用户签收，但任务由 AI 生成执行，日志明确说明，不是“用户七天真实日常工作使用”的等价证据。签收代表当时按已知限制接受交付，不能推出所有功能生产级稳定。

## 14. A/B、留出集、统计检验与漂移检测

### 14.1 一个合理 A/B 应控制什么

只改一个主要变量，固定数据、模型、提示规则之外的参数、工具权限、来源、预算、评分器版本和过滤规则。顺序/并行对照要使用相同子任务，不要只对并行版增加资料；模型对照要记录模型和成本，而不把能力变化归因到提示词。

真实 LLM 有随机性，同一天、同温度仍不能保证完全相同。可以多轮、随机化 A/B 运行顺序、按任务配对，对时延记录环境和限速。

### 14.2 当前 Welch 检验能力

`eval/experiment.py` 实现两独立样本均值的 Welch t 检验，不要求方差相等。

```text
t = (mean_A - mean_B) / sqrt(s_A²/n_A + s_B²/n_B)
```

p 值用于描述零差异假设下的统计证据，不是“B 有 p 概率更差”。还要看效应大小、置信区间、样本独立性和多重比较。

这个模块存在，不证明 12 例留出集已经做了显著性检验。该批记录是单轮任务配对与分组统计；若要统计推断，任务级配对 bootstrap/置换检验或按任务聚类更合适，不能把每个引用对当完全独立样本。

### 14.3 Micro 与 Macro

micro 把所有引用对汇总再算，长报告权重更高；macro 先算每任务比例再平均，任务权重一致。当前 support_rate 总汇总主要是 micro。

新旧报告对数从 338 降至 188，会改变各题的权重。建议同时看任务级配对差异、必要事实覆盖、分组结果，避免整体比例被少数长报告主导。

### 14.4 留出集究竟证明了什么

它提供“规则在选定未见材料上也有整体改善”的方向性证据。12 例不足以证明广泛泛化或排除过拟合；英文与中文同时改变语言和任务形态，也不能单独把差距归因为语言。

严谨回答：“我做了 12 例留出配对对照，整体和两分组均值提升，但存在单题下降，尚未做多轮大样本统计检验。”

### 14.5 漂移检测

`eval/drift.py` 展平数值指标，对冻结基线检查绝对和相对变化；新指标单列，基线指标消失告警。趋势检测还有滑动窗口异常和持续单边变化。

绝对阈值适合比例变化，例如质量下降 0.05；相对阈值适合延迟/成本变化，例如增加 20%。基线为 0 时不能简单除零。阈值告警是退化信号，不是根因诊断；也不能混合不同数据集、模型或分母。

当前能力可以由脚本调用，不应描述成已经部署的全天候线上监控和通知服务。

### 14.6 AutoOptimizer 的边界

它是规则反馈组件：指标超过阈值→白名单参数建议。允许 context_budget/max_output_tokens/max_calls，受硬上下界和每轮变更数量限制，默认 dry-run 并记录审计。

这不是强化学习、自动训练模型或自主改代码。降低输出上限可能缩短延迟，也可能造成草稿、截断和质量下降，建议必须配真实验证。

## 15. 工具执行、预算、权限、HITL 与 MCP

### 15.1 ToolExecutor 执行顺序

工具查找→参数校验→权限集合→风险与审批→有限重试/超时→执行→结果处理。模型输出工具名并不能绕过这些检查。

JSON Schema 校验当前是子集，支持基本类型和 required，多余参数宽容放行，不是完整 JSON Schema 验证器。不应在面试里宣称支持所有嵌套、枚举、范围、格式和 additionalProperties 安全约束。

### 15.2 为什么参数检查和权限检查都需要

参数正确只说明结构可执行，不代表允许做。路径参数可能越出工作区，URL 可能指内网；还需要具体工具实现的边界检查。工具存在不代表当前角色已授权。

当前默认内置工具是 calculator/current_time。资料导入和搜索主要通过应用链实现，不能因为系统会抓网页就说它默认暴露了任意浏览器/任意 shell 工具。

### 15.3 权限收敛

父允许工具 ∩ 角色允许工具 ∩ Skill 允许工具决定最终可用范围。MCP 工具进入同一注册表和执行器，不走“外部工具就免审批”的特殊通道。

权限说明写在 prompt 中只能提示模型，实际拒绝必须由程序执行。这也是 Harness 的价值。

### 15.4 HITL

HIGH 风险或 requires_approval 工具要审批。批准必须绑定具体任务、请求与参数，过期、重复或非待审批请求不能放行；approval_handler 必须明确返回 True。

不要把 bool truthy 与批准混用。待输入、待审批也不同：待输入是任务信息不全，waiting_input 挂起；待审批是已知道具体操作但需要用户决策。

部分 runtime Web pending 审批是内存态，不自动跨服务重启恢复；SQLite 也有独立持久化审批组件，不能混写为所有审批都已持久化。

### 15.5 重试与副作用

只对已分类 transient 且无副作用的工具有限重试。超时、有副作用或非瞬态错误不自动重试。

网络调用超时可能是“服务没执行”，也可能是“执行成功但响应丢了”。自动重试转账、邮件或删除可能重复动作。当前框架不提供通用强制终止进程沙箱；线程超时后后台可能继续运行，同一 Executor 阻止未结束的同名工具重复启动。

### 15.6 根预算和子任务预算

根账本负责整项任务开销；每个子任务若各拿满父预算，会造成预算乘法膨胀。

```text
可派工预算 = 根剩余预算 - 在途预留 - 成稿预留
每个子任务分配 <= 当前派工池约 40%
所有分配合计 <= 派工池
```

reserve 使并发开始前先占额度；settle 用实际估算结算；确认没发出的动作才 release；未知消耗不能当零费用释放。必须给最终成稿留下预算，否则子任务都有输出，根任务却写不出报告。

账本中 child_run 汇总与逐模型调用属于不同记录，不应重复计入调用次数。根账本持有锁保护统计与写入；当前网关调用也可能在锁范围内执行，不能把一个共享账本里的所有请求都说成无阻塞并行。应用子任务按自己的执行上下文运行，再结算回根。

### 15.7 “不超额”为什么只能说护栏

真实用量通常响应后才知道，价格由本地表估算。最后一笔可能越过阈值；外部供应商计价、缓存优惠和失败计费也有差异。

调用前检查阻止继续发起，调用后检查及时停止。未知价格/缺用量时保守停止，不把未知当免费。累计输出 token、调用数、运行时间、费用分别限制，不能互相替代。

Adapter 禁用 SDK 隐藏重试，但 disable_thinking 分支对失败可能再尝试一次不带扩展参数；因此不要说“每个模型调用意图永远恰好一个 HTTP 请求且精确记账”。已有源码里的这条兼容回退需要如实说明。

### 15.8 IterationBudget 与熔断

它控制子任务迭代和失败连击，不是根任务美元账本。连续失败达到阈值进入 open，拒绝继续派工；调用方可显式 reset 进入 half_open 试探，成功后恢复，失败再打开。

当前是进程内机制，不是带冷却定时器、跨节点共享状态的生产服务熔断器。熔断解决重复失败消耗，预算解决总资源上限。

### 15.9 MCP 的最小链路

本地 JSON-RPC/流式 RPC：initialize→tools/list→tools/call，远端工具映射到 ToolSpec 后进入 Executor。安全配置做工具 allow/deny、风险映射和 side_effect 默认。

当前以工具能力为主，初始化使用历史协议版本 2024-11-05；不要宣称已支持所有最新 MCP 能力、远程 OAuth、完整 HTTP 传输、资源和提示管理。A2A 是另一个协议主题，不等于多个 Agent 在本地线程池协作。

### 15.10 密钥与日志

Key 从项目环境配置读取，Settings 的 key 字段不进入普通 repr；异常输出需避免供应商响应体和认证头。演示只显示脱敏配置。

Trace 和工具结果可能包含业务材料，因此不能说“日志天然无敏感信息”；当前安全边界主要是受控输入、配置脱敏和特定异常处理。真实生产还需日志脱敏与访问控制策略。

## 16. SQLite 队列、崩溃恢复、幂等与 Web 工作台

### 16.1 为什么 SQLite 配文件

SQLite 存任务、状态、租约、审批、操作账本等结构化信息；正文、证据、报告和 trace 放任务目录。数据库适合查询与事务，文件适合可读产物与版本复查。

SQLite 状态库启用 WAL、foreign_keys、busy_timeout，单实例用锁包写事务。WAL 有利于读写并存，但仍有单写者限制，不等于任意并发写无锁。参考 [SQLite WAL](https://www.sqlite.org/wal.html)。

### 16.2 队列和租约

queued 任务可领取，running 持有 lease_owner/lease_expires，worker 心跳续租。领取过程在事务内选择候选并用带条件 UPDATE，rowcount 不为 1 则不能认为领取成功。

崩溃后 lease 到期，任务标记 interrupted，才能审计恢复。waiting_input 不在可领取集合；补充后 requeue，避免 worker 在用户尚未输入时抢先执行。

租约主要降低重复领取，不能承诺在任何长暂停和租约过期情况下外部副作用永不重复。生产分布式场景还要考虑 fencing token、操作幂等键和所有权校验；这些属于扩展设计。

### 16.3 文件与数据库不是一个事务

阶段采用“产物先落盘、状态后提交”。如果文件已写而数据库未记完成，恢复需要对账，不能重新生成时无条件覆盖。原子写临时文件再 replace 降低半写文件风险，但不会把文件和 SQLite 变成分布式原子事务。

### 16.4 三种恢复不要混淆

| 层级 | 保存什么 | 当前范围 |
|---|---|---|
| LangGraph MemorySaver | 图会话状态 | 同进程，同实例 thread |
| durable plan | 计划节点与完成结果 | 文件原子更新，按约定重跑剩余 |
| 研究 Job 阶段恢复 | sources/stage_*.json/ledger/SQLite 状态 | 跨进程业务恢复，审计已提交资产 |

恢复不是“从任意 token 接着生成”，而是从已提交阶段或计划单元继续，某些未完成计算会重跑。

### 16.5 操作幂等键和 unknown

`op_key=job_id:action:action_version:params_hash`。成功结果可以回放；进程中断留下 pending/running 的操作启动时标记 unknown，禁止盲目重放。

为什么 unknown 有意义：外部动作可能已执行，但程序来不及记成功。当前宁可要求核实，也不重复执行有副作用操作。不能据此宣称外部 exactly-once；要有外部服务幂等支持才可能进一步保证。

params_hash 是稳定动作身份，不是密码保护、加密或防篡改签名，不应替代安全授权。

### 16.6 取消与超时

排队任务可以直接取消；运行任务置 cancel_requested，在模型/阶段/派工边界收敛，保留已完成产物。正在执行的请求不一定瞬间终止。

时间限制是边界检查与单请求 timeout，不是所有后台线程的强杀。O-18 曾处理电脑休眠被误计为执行时间，属于运行计时策略，而非通用操作系统级任务隔离。

### 16.7 Web 工作台的实际技术栈

`ThreadingHTTPServer`/`BaseHTTPRequestHandler`，内嵌 HTML/CSS/JavaScript，hash 路由五视图：首页、任务中心、任务详情、运行观测、配置与评测。它不是当前 FastAPI+React 服务。

研究任务通过本地持久化队列执行，页面展示阶段、产物、来源、引用核验和版本；通用 Agent 有自己的直接运行入口。UI 的缓存展示不是权威状态，刷新后应读后端产物。

### 16.8 Web 安全与路径边界

本机 Host/Origin/写接口校验、请求体限制，动态内容以文本 DOM 渲染，避免当 HTML 执行。文件读取/导出先规范路径并确认在受控任务根内；Windows junction/symlink 解析也属于边界。

这是本地工具的安全设计，不包含完整多租户身份、企业 SSO、RBAC、TLS、审计运营与公网部署方案。若要公开部署，需新的威胁模型和服务化改造，不能简单绑定 0.0.0.0 就称生产就绪。

### 16.9 SSRF 的具体防线

只允许 http/https，解析主机和 IP，阻止私网、回环、链路本地等危险地址，校验重定向每一跳。抓取连接使用验证后的 IP，减少“验证一次、连接时再解析”的 DNS rebinding 窗口。

HTTPS 连接要保留正确 hostname/SNI/证书校验；Host 头与 IP 固定连接分开处理。单靠字符串拒绝 localhost 不够，因为还有 IPv6、数字编码、重定向和解析结果变化。

### 16.10 导出与已知限制

支持 md/txt/docx；DOCX 采用最小 OOXML，版本化产物不覆盖旧稿。项目需求明确规定来源链接只在本机界面展示，不写入导出；导出仍保留引用标记、来源清单、交付等级与局限。

不要把“导出 docx”说成“输入任意 Word 文档、复杂表格、公式和版式都能解析”。当前 DOCX 输入与复杂排版不是已完备功能。

## 17. 可以展开讲的真实问题与解决过程

这部分用于行为面试和技术追问。只讲你实际理解、参与和复核过的过程，不把日志中的 AI 执行动作说成个人亲手完成。

### 17.1 故事一：引用可定位，但不能支撑结论

**问题**：原有程序验证能保证引用编号存在、摘录在原文，却无法保证结论范围不超出证据。引用越多也不一定更可信。

**定位**：建立断言—证据对判分，发现复合结论挂多引、缺口声明也挂引用等模式。混合集严格支持率仅 66%；需要再限制相同案例范围才能公平对照。

**修改**：初稿规则要求引用贴近直接支撑子句、复合断言拆分、未知/缺口不挂不当引用；审校提示更严格检查支持关系。程序确定性检查和交付语义保持原有范围。

**验证**：当前缓存同 v3 范围约 69.5%→88.7%；12 例留出配对 60.1%→73.4%。同时看交付、分组与可读性，避免只优化比例。

**反思**：引用对数量减少，部分单题下降，未引用断言覆盖仍需另查；复杂英文多来源严格支持率为 68.8%，不能宣传已全面解决幻觉。

可回答的关键追问：“为什么没有单纯增加 Reviewer 次数？”因为先量化和归因，改两个相关规则比盲目增加调用更小、更可评估。

### 17.2 故事二：研究任务没有产物，触发输出预算

**问题**：Q4 D1 的部分写作任务在前置阶段就耗尽输出预算，交付 draft 且无报告。不能只说模型表现不好。

**定位**：账本显示调度结构化输出反复失败，提示词没有字段级 schema；多来源证据抽取在结构上需要更多调用；推理型模型隐藏 thinking 也计入 completion，使可见短 JSON 占用更多输出预算。

**修改**：调度提示词明确契约示例；应用默认调用数/累计输出上限从 12/8192 调到 40/65536，费用和时间护栏不变；短结构化阶段关闭 thinking，写作保留需要的推理配置。

**验证**：历史日志记录 T03 复跑链内 accepted，19 次调用、21723 token、约 99.7 秒；这是修复验证，不替代任务内容的人工业务验收。

**反思**：预算需按业务结构校准；提高上限不能解决错误的结构契约；关闭 thinking 的 Adapter 兼容回退有额外请求边界，不应承诺精确一请求记账。

### 17.3 故事三：请求派生丢字段，部分模式无可用资料

**问题**：不同入口或编排模式出现资料/参数丢失，模型收到空资料后不能完成，像质量问题，根因却在工程接线。

**定位**：比较根 TaskRequest、子请求和产物快照，检查 workspace_root、输入、profile、预算和网络策略是否传到执行层；O-17 还涉及 workspace_root=None 缺省处理。

**修改**：子请求从父请求 dataclasses.replace 派生，显式修改差异字段；工作区缺省与应用侧保持一致。显式零预算保留为零，不能用 truthy 判断把它当不限。

**验证**：针对丢参路径加最小回归与真实模式复验，不通过重复调 prompt 去掩盖空输入。

**反思**：模型任务失败未必来自模型。要先查输入、权限、预算、状态，再分析语义质量。

### 17.4 故事四：记忆换位置，却没有缓存代理收益

**问题**：初始对照里 system 前缀确实稳定，但 user 注入与 system 注入的整体前缀占比几乎无差异。

**定位**：Context Budget 对权重重新归一化，消息份额被挤占，历史窗口恒两条，能复用的历史本来就很少。

**修改与结果**：修复消息份额保留后，同一结构性对照里 user 模式前缀占比由 system 模式的 42.4% 提到 71.3%。

**当前事实**：历史窗口修复默认已开，但当前 memory_in_user_message 默认仍 False；三层 Provider 也没有默认接入 Runtime。讲清“已验证配置”和“默认产品行为”的差别，比只报 29pp 更能体现工程判断。

### 17.5 故事五：待用户输入，却被 worker 提前执行

**问题**：UI 显示需补充，但后台状态仍 queued，常驻 worker 会领取并执行，导致逻辑与界面矛盾。

**修改**：增加 waiting_input 挂起，不允许 worker 领取；用户补充后 requeue，再触发执行；取消和恢复也要收敛。

**验证**：针对“worker 持续存活时待输入任务仍应挂起”的回归验证，而不是只截图表单。

**学习点**：异步 UI 状态必须映射真实后端状态，不能只改按钮文字。

### 17.6 故事六：评审数组输出全部解析失败

**问题**：首次支持率评审 71 批输出未形成可用判定，仍花费约 $0.095。模型要求输出数组，但共享 extract_json 只接受对象。

**修改**：在本判分脚本局部增加数组容错解析，保留共享对象解析器的既有契约；增加 unparsable_batches 记录。

**反思**：JSON 合法不等于返回类型符合调用契约。失败判分不能当 0 支持率，也不能按空结果排除而产生虚高统计。

## 18. 高频追问与回答示例

回答时优先给结论，再给代码落点和一个例子，最后说明真实限制。

### Q1：你为什么做这个项目？

我想把研究写作从一次聊天变成可核验的工作流，重点是资料来源、结论支持、过程控制和版本交付。多 Agent 是解决独立子题分工的方法，不能替代证据与验收。

### Q2：和普通 RAG 有什么区别？

检索只是一个环节。系统还要决定如何拆任务，抽取可定位证据、安排写作和审校、控制预算、处理拒答与恢复。但当前知识检索并非企业级神经向量 RAG，不能与第一项企业项目的混合搜索、reranker 和 vLLM 混说。

### Q3：是不是把几个提示词串起来？

角色提示词只是职责层。实际还有 TaskRequest、计划契约、权限交集、根账本、依赖波次、来源存储、quote 校验、阶段恢复和质量分级。可以打开 evidence、review 和 ledger 解释一个任务，而不只展示回答。

### Q4：所有编排都在 LangGraph 里吗？

不是。通用 Agent Loop 用 StateGraph，业务研究编排还用 Python 执行器和线程池，阶段恢复靠文件与 SQLite。LangGraph 是底层运行组件，当前没有将全部业务模式塞进一个大图。

### Q5：为什么用线程池而不是 asyncio？

当前模型和工具接口以同步调用为主，小规模本地并发用线程池更直接。asyncio 能提高大量 I/O 连接的组织效率，但要改 Adapter 和取消传播；当前最多 3 并发，没有必要为了形式统一大范围重写。

### Q6：遇到一个子任务失败怎么办？

在受控范围内有限重试；仍失败明确记录，其他分支按策略继续；汇总保留缺口并进入统一审校，不能默默丢掉失败分支后把报告判成完整成品。是否降级/重规划取决于预算和依赖。

### Q7：Manager 拆错了怎么办？

结构错误由程序契约校验拦截；语义拆题错误依靠覆盖检查、Review 和受控重规划处理。结构合法不代表计划合理，不能承诺自动拆题完全正确。

### Q8：为什么多 Agent 不一定提高质量？

同模型角色的错误相关，更多文本会带来噪声和错误传播。独立子题适合并行；简单题优先 single/fixed，避免无收益的通信和成本。

### Q9：EventBus 是 Agent 通信协议吗？

这里是进程内观察事件总线，用于派工、阶段、结果和 Trace 订阅。业务结果传递仍靠任务输出与中间产物。它不是跨进程 A2A 或可靠消息中间件，而且默认主流程没有完整统一总线接线。

### Q10：66.5% 怎么测？

6 个等待桩任务，3 并发，50 轮顺序/fanout 对照，均值 0.902s 对 0.302s。它验证并发机制，不代表真实全链报告都快 66.5%。

### Q11：81.6% 是 API 账单减少吗？

不是。17 技能的注入文本用项目粗略 tokenizer 估算，全量 5819，对照平均 1073；不含其他上下文和输出。实际费用需看供应商 usage。

### Q12：Skill 真执行了什么？

激活后将任务方法注入上下文并收紧工具权限，模型照指令完成任务，实际动作由工具执行器执行。它不是动态加载任意代码，deactivate 也不是卸载操作系统资源。

### Q13：三层记忆全接进默认 Agent 了吗？

目前组件实现和测试成立，默认 Runtime 仍用 LongTermStore JSON 检索，三层向量门面用于单独实验和可替换组件。需要明确接入才能把它称为默认端到端能力。

### Q14：74% 是什么 embedding？

稳定特征哈希，默认 256 维，结合 BM25 与衰减重排。不是神经 embedding。实验是 100 条改述查询的 Hit@3，历史后端是 sqlite-vec 的适配标签。

### Q15：为什么语义记忆不随时间删除？

访问少不意味着事实失效，因此只降排序；任务经历更可能过时，可按阈值清理。但事实更新需靠来源、版本和显式更正，不能只靠是否被访问判断。

### Q16：29 个百分点是怎么得到的？

5 轮消息模拟，对比动态记忆放 system 与 user，两轮相邻消息的完整相同前缀估算占比由 42.42% 到 71.33%。这不是服务商缓存统计，而且当前默认注入开关仍关闭。

### Q17：有引用为什么还可能幻觉？

引用可找到，但内容可能只支持结论的一部分，报告可能扩大人群、时间或条件；来源本身也可能不可靠。程序守定位下限，模型与独立评审查语义支持，人工判断高风险事实。

### Q18：你如何保证证据不伪造？

摘录必须在导入正文逐字找到才入库，保留来源与定位。它保证“摘录确实存在于这份输入”，不能保证原网页真实或模型 fact 无推断，需要下一层审校。

### Q19：96.7% 是 42 例的成功率？

不是，是 v3 30 例简单集的预期行为符合率，19 成品加 10 正确拒答等于 29。另 12 例留出集专门对照，不能把两套分母混在一起。

### Q20：为何 eval 显示 failed=11，还说符合 29？

旧 totals.passed 只算 accepted，10 个应拒答的 unable 也记在 failed，但它们的业务预期是拒答。要读 expected_outcome，不能把运行计数直接当业务正确率。

### Q21：88.7% 达到 95% 门槛了吗？

严格口径没有；含部分支持的宽口径是 96.5%。二者不能混用。复杂留出多来源只有约 68.8%，还存在质量缺口。

### Q22：66%→88.7% 是多少提升？

首先不能直接算作同口径收益。66% 混合集，88.7% 是 v3；当前缓存限制同 v3 后基线约 69.5%，差约 19.2pp。最稳的配对泛化描述是留出集 60.1%→73.4%。

### Q23：人工一致率 85% 可靠吗？

日志记 17/20，但若没有本人独立盲标原始表，我不会拿它声称严格人工一致性。20 对即使真实也太少，只能作为探索性校准。

### Q24：怎么避免评测集过拟合？

固定版本和规则，不把答案传给执行者，保留未见材料做同题配对，并看分组、单题和质量覆盖。当前 12 例只提供方向性证据，不声称已经排除过拟合。

### Q25：有证据就一定 accepted 吗？

不一定。证据可能不覆盖任务核心、语义支持不足、章节缺失或报告自述无法完成。accepted 是链内判断，还要独立业务质量复核。

### Q26：禁止表述出现就自动拒收？

当前字面命中为 warn，避免把否定引用当违规；必要章节缺失是 error。语义违规由模型/独立评测/人工判定，不能宣称所有禁语都会强拦。

### Q27：预算怎么保证并发不花三份钱？

共享根上限，派工前扣除在途与成稿预留，子任务取限定份额，完成后结算。它限制累计估算开销，最后一笔实际计费仍可能超过阈值。

### Q28：超时后你能停止工具吗？

线程超时只是及时返回等待，不能杀掉正在运行的函数。当前阻止同名重复启动并禁止超时自动重试；强杀与副作用隔离需要独立进程或外部服务设计。

### Q29：恢复能保证只执行一次吗？

已提交阶段可复用，未知副作用不自动重放。不能保证外部 exactly-once，只有外部系统支持幂等键并有核实机制才能进一步保证。

### Q30：为什么不用 PostgreSQL、Redis 和消息队列？

当前是本地个人系统，SQLite+文件的部署和排查成本低。跨用户、大量并发和分布式执行需要更强的数据库与队列，但没有为尚未需要的规模预先引入复杂基础设施。

### Q31：如果要上线给企业用，你先改什么？

先明确数据与权限边界，设计认证/租户隔离、工具沙箱、日志脱敏与持久化执行所有权，再完善评测集和语义质量。之后才考虑服务框架、队列和数据库扩展。这里只是演进方案，当前个人项目不冒充企业级部署。

### Q32：你用了 AI 辅助，自己的价值是什么？

按真实经历回答：需求取舍、架构边界、代码理解、错误复现、实验口径、验收判断，以及能独立解释和修改关键链路。不能用“独立项目”回避辅助工具，也不能只背生成文档。

### Q33：项目目前最大的不足是什么？

语义支持仍受复杂材料影响，小样本评审存在不确定性；三层记忆/Provider/用户注入/EventBus 的默认主流程接入与组件描述有差距；工具超时和外部副作用没有通用强终止/ exactly-once 保证。按用户需求逐项完善，不把所有不足都靠加 Agent 解决。

### Q34：下一个最有价值的改进是什么？

如果目标是简历能力一致，先明确并补齐组件默认接入与文档口径；如果目标是业务质量，先用更多多来源任务检测无引用断言、引用覆盖和支持关系，并复核来源可信度。先定目标与验收，再选实现。

### 23.1 数据 D1：3 并发与平均耗时降低 66.5%

**推荐口述**：

> 这个数字来自离线机制实验，不是真实研究报告全链提速。我们用同一个 worker 桩跑 6 个独立子任务，每个等待 0.15 秒，分别顺序执行和 3 并发 fanout，做了 50 轮。保存报告的顺序均值是 0.902 秒，并行均值是 0.302 秒，各轮耗时降低比例的平均值约 66.5%，加速比约 2.99。它证明线程池能有效重叠 I/O 等待；真实报告还包含串行合并和审校，所以不能直接推广。

**证据与公式**：`resume_metrics.parallel_speedup`；计时器为 `perf_counter`；主读数为 `mean(1-T_parallel_i/T_sequential_i)`，不是所有时间总和之后再算比例。6、3、0.15、50 必须一起记。

**D1-Q1：为什么恰好接近 66.7%，是不是按理论捏的？**

6 个等时任务顺序是六段等待，3 并发是两波等待，理想耗时比 2/6=1/3，降低 2/3。记录来自实际计时，线程建立、任务提交和汇总使结果略低于理论值。这个设计本来就接近理想上限，不能把近三倍当复杂任务普遍表现。保存 JSON 有均值、标准差和中位数，但没有 50 轮原始时长列表，因此不能声称保留了完整样本分布。

**D1-Q2：50 轮证明稳定吗？标准差是多少？**

保存报告顺序标准差约 0.0006 秒，并行约 0.0004 秒；中位数约 0.902/0.3019 秒。这说明这次低负载等时等待实验抖动小。它不涵盖模型服务长尾、限流和网络变化。标准差小是实验环境简单，不等于真实请求同样稳定。

**D1-Q3：为什么用平均值，为什么不报 p95？**

均值表达平均等待成本，中位数表达典型请求，p95 表达尾部体验。当前报告没有 p95 字段，也没有原始列表可精确补算，不能临时编一个。若做真实性能实验，应保存每轮样本、明确分位数算法，并一起报告均值/p50/p95、错误率和费用。

**D1-Q4：不同任务时长下还有效吗？**

脚本有 0.5–1.5 倍随机等待的 jitter 场景，保存的平均降低约 59.46%、加速约 2.5 倍。但串行和并行使用连续随机数调用，不是每轮重用完全相同的时长向量；它是分布层面的机制测试，不是严格相同负载的任务配对。更严格方案应预生成每题时长，并在两臂复用，再随机化先后顺序。

**D1-Q5：Python 有 GIL，线程为什么能提速？**

常规启用 GIL 的 CPython 中，多个线程不能同时执行多路 Python 字节码，但等待网络或 sleep 时可让其他线程推进，所以 I/O 等待能重叠。CPU 密集型 Python 循环要考虑进程或释放 GIL 的原生计算。不能将这份 sleep 实验解释成 CPU 算力提高三倍；Python 也有可选自由线程构建，不能说所有版本永远受同一 GIL 约束。

**D1-Q6：增加到 10 个 Agent 会更快吗？**

不一定。子任务数、依赖关键路径、串行成稿、模型限流和预算都会限制收益；更多线程还可能增加排队和失败。当前并发上限 3 是本地系统资源和预算约束，不是经过全局最优化证明的最佳值。若优化，应扫 1/2/3 等并发度，比较相同任务的全链质量、时间和成本，不只看最快一个样本。

**D1-Q7：并行版和顺序版工作量相同吗？**

等时桩的子任务数量和 worker 相同，fanout 还计入组合文本与线程池开销；没有真实调度 LLM、检索或 Reviewer。真实比较必须固定任务拆分、相同资料和输出要求，并计入合并与审校，否则可能只是少做了工作。

**D1-Q8：怎样设计可信的真实模型性能对照？**

这是后续方案：固定案例、模型、预算、来源与质量门槛；先确定同一子任务图；多轮交替/随机运行顺序；记录请求耗时、全链耗时、限流、重试、失败、token 和费用。质量下降的快结果不能直接算优化成功。按任务配对比较，再按独立任务重采样估计差异区间。当前没有这些全链提速结果，不伪装已经测过。

### 23.2 数据 D2：技能注入 token 降低 81.6%

**推荐口述**：

> 我比较的是技能上下文，不是整项任务费用。基线把 17 个技能全文都注入，对照只放全部摘要和一个命中技能全文。每个技能轮流作为命中项，17 种组合的平均节省约 81.6%，最小约 78.7%，最大约 84.8%。token 是项目启发式估算，约从 5819 到平均 1073。这个实验验证渐进加载的开销收益，不直接证明路由准确率或模型总成本同幅下降。

**D2-Q1：17 次实验是 17 次模型请求吗？**

不是。是遍历 17 个技能，构造对应字符串并估算 token，不需要模型。完整上下文和实际生成效果没有在这条指标里评测。把 17 种静态组合称为样本覆盖可以，但不能说做了 17 次真实账单测试。

**D2-Q2：估算 tokenizer 怎么写，为什么不用模型 tokenizer？**

`estimate_tokens` 对中文基本汉字计数，其他字符约按四字符一个 token 粗算，是轻量预算近似。真实 tokenizer 会受文字、标点、编码和特殊 token 影响，同样字符数不一定同 token 数。它适合组件比较和软预算，不能据此作精确计费。使用目标模型 tokenizer 或实际 usage 对照是可改进方向，当前数字必须带“估算”。

**D2-Q3：这个基线是不是太弱，实际没人注入所有技能？**

确实是一个朴素全量注入基线，目的是量化上下文增长成本。它说明比全量方式省，不说明比所有合理路由方案都省。更强对照可包括关键词选单技能、BM25 选 top-k、模型 rerank、压缩摘要等；要同时看误路由与业务质量。这些更强对照未包含在 81.6% 内。

**D2-Q4：需要两个技能、依赖和 references 怎么办？**

多个全文、依赖正文和长 references 都增加对照分母中的实际注入量，节省可能更小。当前指标一次一个命中全文，不计这些附加材料。依赖激活与依赖正文注入也不是同一事实。实际任务应记录真正注入内容，不能假设所有任务都保留八成收益。

**D2-Q5：路由调用本身是否把省下的 token 花回去了？**

可能。总输入应包括候选路由、主 Agent、后续审校等所有调用的输入，而非只看主 Agent 的 Skill 片段。可以先用便宜 BM25 限候选，必要时再模型 rerank；是否划算取决于技能数量与调用次数。当前指标不含路由模型的总成本，不能做净费用承诺。

**D2-Q6：减少上下文会不会漏知识导致效果变差？**

会，所以需要路由命中率、NO_SKILL 合理性、任务成功率和误遗漏评测。低 token 高质量才有意义。当前默认路由支持失败兜底，但没有从 81.6% 得到业务无退化结论。

**D2-Q7：随着技能数量增长，复杂度是什么？**

全量全文成本约随各正文总长度增长；摘要全量+少数正文仍随摘要数量增长，只是增长更慢，并非常数。技能多到候选摘要也过长时，可先索引召回少量候选，再加载正文。当前注册表扫描和 BM25 检索不是千万级服务，规模边界应如实说明。

### 23.3 数据 D3：Top-3 记忆检索命中率 74%

**推荐口述**：

> 这是 100 条构造改述查询的组件实验。每条查询有一个指定正确记忆 ID，正确 ID 在前三即命中；74 条命中，所以 Hit@3 是 74%，Top-1 为 60%。历史实验用 sqlite-vec 适配后端、256 维哈希嵌入、BM25 重排和衰减。按这 100 条结果做 2000 次 Bootstrap，保存的 95% 区间约 65%–82%。它不是神经语义检索的大规模正确率，也不能证明默认 Agent 已接入这条组件路径。

**D3-Q1：为什么叫 Hit@3，不叫 Recall@3？**

这套标注每题一个指定 ID，计的是“至少一次命中”二元事件。多个相关文档时 Recall 要统计召回的相关数占全部相关数；Precision 看返回结果中相关比例；MRR 看首个相关排名的倒数。当前单 ID 条件下 Hit 与该特定 recall 数值可能相同，但指标定义不能随意推广。

**D3-Q2：100 条数据怎么来，有没有额外干扰？**

当前脚本有 100 组事实/改述 query，写入对应目标知识；其他目标知识也互为候选干扰。旧文档宣称另外 100 条干扰，但当前脚本和 JSON 无法确认。不要声称在 200 条候选上测过。人工构造主题较集中，可能偏向词面相关，样本代表性不足。

**D3-Q3：跨会话到底测了什么？**

脚本先用 session_A 标签写入语义记忆，再以另一轮查询读取，核心是可复用知识不依赖当前工作记忆。它没有单独证明关闭进程、重建索引后仍命中，也没有验证默认 Runtime 的分层 Provider 注入。因此“组件跨会话可复用”与“所有默认用户路径跨进程长期记忆完善”要区分。

**D3-Q4：为什么 74%，不是 78%，为什么不报 80%？**

保存结果逐条可数到 74/100，不能挑旧小样本更高数字。100 条也不大，26 次未命中需要按同义改述、候选不足、哈希碰撞、词面/主题噪声和衰减进行错误归因。未做归因时不能声称已知道全部失败原因。

**D3-Q5：Bootstrap 2000 次是不是相当于 2000 个真实样本？**

不是。每次从原 100 条命中记录有放回抽 100 条，算一次命中率，得到 2000 个统计重采样值。独立信息仍来自 100 条 query。增加重采样次数使区间计算更稳定，不消除样本选择偏差，不把真实样本量变成 200000。

**D3-Q6：为什么用 Bootstrap，区间意味着什么？**

它可以不指定复杂检索分布，通过经验样本估计指标波动。当前是 percentile 区间；二元命中也可用 Wilson，教学计算约 64.6%–81.6%，与保存 Bootstrap 区间相近。频率学派 95% 指重复按同方法取样构区间的覆盖性质，不是“当前固定真实率有 95% 概率在这个区间”。两个区间都依赖代表性和独立性，不能替代新业务测试。

**D3-Q7：哈希向量、BM25、衰减各贡献多少？**

没有对应消融数据就不能分配贡献。应该用相同 query、候选和冻结时间做 hashing-only、BM25-only、hybrid、hybrid+decay 对照。查询会强化 stability，所以做多臂时必须每臂重置存储或冻结强化，避免先测那一臂影响后面结果。当前 74% 是组合组件结果，不是每项单独收益。

**D3-Q8：Top-3 换 Top-10 是否自然变高？**

固定排序与候选不变时，Hit@k 随 k 增大不会下降，但更多上下文会增加噪声、费用和错误引用。当前层 search 会随 k 改变过召回数量及重排候选，直接重跑也可能改变前几位；严格比较应固定排名列表再截取 k。应同时看任务质量而非无限放大 k。

**D3-Q9：百万条记忆还能用吗？**

当前组件面向小规模本地，哈希内存回退遍历向量，索引和元数据恢复也要考虑。扩展可选神经 embedding、ANN、分区和多用户隔离，但要测召回/时延/索引构建与更新成本。不能因为 SQLite 扩展支持向量表就承诺百万级生产 SLA。

### 23.4 数据 D4：提示前缀稳定度提升 29 个百分点

**推荐口述**：

> 我测的是缓存友好结构的代理指标，没有读取供应商实际缓存统计。5 轮模拟里动态记忆每轮变化，比较它放 system 还是 user。启用历史份额修复后，开头连续相同消息的估算 token 占比从 42.42% 到 71.33%，差 28.91 个百分点。当前代码的 user 注入仍是显式开关、默认 False，所以应该说机制对照有收益，而不是默认请求已获得真实缓存费用收益。

**D4-Q1：29% 与 29 个百分点有什么区别？**

百分点是两个百分比直接相减：71.33%-42.42%=28.91pp。相对增长是 28.91/42.42≈68.2%。这两种都不是费用下降比例。若使用“提升 29%”会让分母不明，应写“28.9 个百分点”。

**D4-Q2：你测了 system 字节稳定还是整个请求前缀？**

system 完整文本稳定是一个布尔检查；前缀占比是从 messages 头部逐条比较 role/content，只累计完整相同消息，第一条不同就停。它没有包含工具 schema、序列化标记或不同消息内部共同 token 子串，不能等同于供应商实际 token prefix 匹配。

**D4-Q3：把记忆放 user 就一定缓存好？**

只有变化位置后移且前面的消息/工具保持相同才可能增加可复用前缀。滑动窗口删除首段历史、技能切换、模型切换、请求选项变化都可能破坏命中。短于缓存最小粒度的前缀也可能没有实际收益；具体规则需看所用供应商，不能用这个组件实验推断。

**D4-Q4：缓存是不是把上次回答拿回来？**

通常这里讨论的是输入前缀计算复用，模型仍可能重新生成不同输出，不是应用答案缓存。应用缓存可以直接返回已保存结果，但有数据时效和任务身份问题，属于另一层。项目这个指标不是答案命中率。

**D4-Q5：为何历史窗口修复前没有收益？**

可复用历史太短，稳定 system 占比不能自动变成大比例共享上下文。修复 messages/reserve 份额后，user 放置方式能保留更多相邻相同历史。它证明两个配置交互会影响收益，不能只归因“改了一个消息角色”。

**D4-Q6：怎么验证真实收益，又怎样避免混杂？**

后续方案是同模型、同任务和同工具，重复相同前缀，记录供应商返回的实际 cached input usage、总 token、费用和延迟；明确冷启动、热请求、过期和不同 prefix 长度。模型答案质量要检查，历史窗口和角色改变要单独对照。目前没有这些真实缓存读数。

**D4-Q7：注入 user 是否能防 prompt injection？**

消息分层有助于将外部数据与静态规则分开，但不能保证模型完全不听从材料内指令。要用清楚的数据边界、工具权限和操作审批限制后果，来源内容不能自动获得系统权限。`<<CONTEXT>>` 是约定标记，不是密码学安全隔离。

### 23.5 数据 D5：42 例评测与预期行为符合率 96.7%

**推荐口述**：

> 42 是两套转换集的总任务数：30 例简单集加 12 例留出集。96.7% 只对应纪律版简单集一次真实批次的 29/30，其中 19 个有答案任务交付成品，10 个无答案任务正确拒答，另 1 个有答案任务为草稿。它衡量预期行为，不是 42 例准确率、复杂研究完成率或全任务报告成品率。

**D5-Q1：为什么不直接用原数据集 EM/F1？**

原 MRC 指标对答案串或词重合，平台输出报告、引用、局限和拒答，需要结构与行为指标。若只看字符串命中，报告可以包含答案却扩大范围、漏引用；拒答也有不同期望。转换集用于工程机制，不代表原公开榜单分数。可另外测短答案 EM/F1，但当前不把这两种任务混用。

**D5-Q2：公开集每个来源多少例？**

简单 v3：CMRC2018 20、DuReader 无答案 10；留出 v3b：DuReader 有答案 6、HotpotQA 多来源 6。数据版本、raw_id、seed 和 source→quote 映射需一起保留。42 很小，且不同类型难度不同，不能将总量写成大规模 benchmark。

**D5-Q3：正确拒答为何计成功？**

该题提供材料没有目标答案，期望就是不要编造；正确 unable 因而预期符合。但它不是“生成了可用报告”，所以同时报告成品比例 19/30 和有答案子集 19/20。评价目标不同，分子不能共用。

**D5-Q4：你是不是靠全部拒答拿高分？**

若所有题都拒答，有答案 20 题全不符合，只能得到 10/30。需要分别报告有答案接受、无答案拒答、错误回答、过度拒答四种结果。当前混合单轮分布是 19 accepted/1 draft/10 unable；进一步验证要扩大可答/不可答覆盖并检查拒答理由，不只看等级词。

**D5-Q5：为什么 30 例能推出 96.7%？可信区间多大？**

96.7% 是这次样本观察值。按独立同分布二元假设做教学 Wilson 区间约 83.3%–99.4%，说明总体率仍很不确定。这不是历史报告已有置信区间，也不解决选择案例偏差。应讲“选定简单样本单轮 29/30”，不讲服务长期达到 96.7%。

**D5-Q6：有没有答案泄漏？怎么确认闭卷？**

检查生成者实际请求是否只有材料与任务，不把评分 key_facts 当隐藏答案注入；禁用自动检索并记录联网策略；评分侧再对照答案。提供包含正确答案的来源是正常资料检索任务，直接告诉模型参考答案却称盲测是不一样的。历史报告有提示效应 caveat，不能仅靠元信息 closed 断言没有泄漏。

**D5-Q7：30 例只跑一次，模型随机性怎么办？**

单轮只是结果快照。同温度也不保证输出一致，需要每例多次、固定版本、统计等级一致性与成本；保存每次输出，不挑最好一次。现有 Q2 有每例多次的历史批次，但它不是同一个 v3 实验，不能借它充当 v3 已重复三轮。

**D5-Q8：留出集既然 12/12，为什么不写 100%？**

可以写观察结果 12/12，但须带样本和单轮。小样本 100% 容易被误读为普遍完美，且等级符合不等于每条引用都支持：留出严格支持率只有 73.4%。把任务符合和细粒度事实支持同时报告更有说服力。

### 23.6 数据 D6：独立模型与人工一致率 85%

**推荐口述**：

> 现有日志记载抽检 20 对、17 对一致，但我没有在仓库找到逐条独立人工标注表。若不能补出真实本人盲标记录，我会删掉简历这个数字，不把它当已验证人工准确率。即便有记录，17/20 也只是小规模观察一致率，不能证明全部自动评审正确。

**D6-Q1：人工是谁，有没有先看模型结果？**

这必须按真实经历回答，不能由文档生成身份。先看模型再“同意”会产生锚定偏差，和独立盲标不同。理想记录是先独立写标签与理由，再显示模型判定做裁决；没有原始记录就明确不确定，不补造。

**D6-Q2：一致率为何不是准确率？**

一致只表示两个判断相同；两个判断可能一起错。准确率需可信 gold label。独立人类也是有分歧的，复杂推断要有裁决标准。claim 本身支持一部分时 supported 与 partial 的界线必须预先定义。

**D6-Q3：类不平衡会不会造成虚高一致？**

会。如果 90% 样本都是 supported，两人总选 supported 就很高一致。需要混淆矩阵、分层抽样和每类指标，也可计算扣除机会一致的 Cohen's kappa。当前没有逐条双标签就不能计算实际 kappa 或每类错误。

**D6-Q4：17/20 的不确定性多大？**

教学 Wilson 95% 区间约 64.0%–94.8%，且只有在观测相对独立、样本代表目标总体时才有合理推断含义。分层抽样未加权时未必代表全样本一致率。这些计算说明 85% 不该以高精度背书模型质量。

**D6-Q5：抽多少样本才够？**

先确定允许误差、置信水平和分层。独立二元样本的粗略最坏情况估算 `n≈z²×0.25/e²`，95%、误差±5pp 约 385 条；±10pp 约 97 条。评审对来自同报告有相关性，设计效应、类稀缺和人工成本需另外考虑，不能把 385 当保证值。

**D6-Q6：是否需要第二个人？**

关键语义可由两人盲标再裁决，提高发现标准歧义的机会。还要记录分歧原因，而非只报一个一致率。个人项目可先少量高风险抽检，但简历应描述实际做法，不承诺已建立专业标注团队。

### 23.7 数据 D7：66%→88.7%、严格与宽口径

**推荐口述**：

> 66% 是旧 34 任务混合集，88.7% 是新 30 例 v3，不能当同范围对照。按当前旧缓存只过滤 v3 案例，得到 296/426≈69.5%，新结果是 228/257≈88.7%，改善约 19.2pp。标签只有 supported 计严格；partial 也计入时是宽口径 96.5%。改动是更精确的引用范围和审校规则，而非换更强写作模型。

**D7-Q1：为什么旧文档写 69.1%，你现在说 69.5%？**

当前缓存的已过滤 pair 和 verdict 可重算成 296/426，原日志提到不同 pair 数及约 69.1%。可能涉及解析/过滤版本，但没有完整中间产物不能精确还原差异原因。以当前可复核数据说明，并保留版本冲突，不硬凑成原数字。

**D7-Q2：分母 426→257，是不是删掉难断言做漂亮数据？**

这是必须正面面对的风险。规则减少一句多引、给缺口不当挂引用以及冗余引用，所以可评价对数下降。支持比例提高不自动等于任务内容更完整。还要检查事实覆盖、缺口声明、报告长度、未引用事实、任务交付，不能只看一个 ratio。当前可以报告观察改善，但没有覆盖指标就不能排除所有“少说少错”效应。

**D7-Q3：断言和 quote 怎么匹配？一句多引怎么算？**

解析报告引用单元，按 evidence_id 回溯 quote，再对 unit—quote 逐对判标签；一个带两个引用的单元会形成两对。若单元是复合命题，每对可能只支持部分，所以需拆分直接支撑子句。合法多跳结论可能需要多证据共同支持，单对评分可能低估集合支持，应另用多证据集合评审，当前不能宣称已完美处理。

**D7-Q4：strict 88.7% 的分子是 228，支持的断言也恰好 228 条吗？**

不一定，是 228 个断言—证据对被判 supported。同一断言多引会有多对，同一个证据也会被多个断言复用。不能换算成 228 个独立正确事实，更不能将 257 对当 257 个独立任务。

**D7-Q5：96.5% 已达到 95%，为什么还说有问题？**

因为这是含 partial 的宽口径，而且只限定简单集和已被引用的对。strict 仍有 20 partial、9 unsupported；复杂材料更低。门槛必须事先确定用哪种口径，不能结果出来后选择更容易通过的口径。

**D7-Q6：为何不直接给 228/257 算置信区间证明显著？**

同报告里的对共享写作风格、来源和模型错误，不能当完全独立 Bernoulli。独立假设教学 Wilson 会约 84.3%–92.0%，但它可能低估不确定性，不宜作正式结论。任务级或报告级 cluster bootstrap、每题多次更合理；目前未有这套正式推断结果。

**D7-Q7：无引用断言是否进入分母？**

通常不会进入带引用 pair 测量。模型删引用后支持率可能提高，但事实覆盖下降，因此必须把“有引用支持率”与“应引用事实的覆盖率”联合评估。没有覆盖数据就不能称全部报告 groundedness=88.7%。

**D7-Q8：独立评审模型会不会对新版文风偏爱？**

会有风格和长度偏差。应隐藏版本标签、随机化呈现、冻结判分规则，人工抽检分歧，并检验多 Judge 稳健性。当前使用不同模型名降低自评风险，但同家族偏差和自动评审误差仍在；不能说独立就完全客观。

### 23.8 数据 D8：12 例留出集，60.1%→73.4%

**推荐口述**：

> 我用同一 12 题分别运行旧、新规则，严格支持率 micro 从 203/338=60.1% 到 138/188=73.4%。中文六题和英文多来源六题的分组均值都改善。但任务级重算是 8 题提升、4 题下降，macro 从约 64.0% 到 72.7%，差 8.7pp。它提供未见材料上的方向性证据，样本小、单轮，还没有完成正式显著性和多轮复验。

**D8-Q1：micro +13.3pp，macro +8.7pp，为什么不同？**

micro 按引用对加权，长报告权重高；macro 每题等权。新旧对数与题目长度变化使权重变化，两者不等。若只报 micro 容易被少数长报告主导，回答时同时给任务级结果更完整。

**D8-Q2：4 题退化，是不是没有泛化？**

说明效果不一致，不能说所有题无退化。整体改善仍是一个观察，但需分析下降题的复合推断、语言、引用范围与内容覆盖，不能用整体数字遮住。泛化是未见分布上的整体表现与稳健性，不要求每个样本必增，但小样本不足以强结论。

**D8-Q3：8/12 赢，能称显著吗？**

不能凭多数就称显著。若只用提升/下降符号做二项双侧 sign test，在独立无平局假设下 8 比 4 的 p 值约 0.388，不构成常用 0.05 水平证据。这个教学计算不使用提升幅度，与配对比例 bootstrap 是不同检验，也不替代多轮真实实验。

**D8-Q4：为什么每条引用不直接做 Welch t-test？**

对是二元/多类判定且同题相关，新旧对数还变化；把所有 pair 当独立样本会伪重复。Welch 模块面向独立组均值，不能机械套到同题配对。应以任务为单位保留 A/B 配对，计算每题差值并做配对 bootstrap/置换，必要时多级采样。

**D8-Q5：你怎么保证留出集真未见？**

能确认的是项目规则调试时没有用这组材料，转换脚本和日志保留了来源/版本。不能证明公开资料从未进入基础模型预训练，所以不是模型层的无污染测试。应避免后续反复用留出集调规则再继续称未见；用过之后需另设新留出集。

**D8-Q6：为什么英语多来源只有 68.8%？**

同时变化了语言、来源数和干扰形态，不能只归因英语。集合证据支持、跨语言表达、长材料截断、错误引用都可能影响；需要单因素分层或错误标注后才定因。它说明简单集 88.7% 的绝对水平不能推广。

**D8-Q7：如何强化这个实验？**

后续方案：预先冻结规则、评分器和主要指标；扩展未见任务，按题配对多轮并随机先后；同时报告 micro/macro、覆盖、拒答、时延和成本；以任务为独立单位做区间和误差分析。没有做完就说“计划”，不能声称已经显著证明泛化。

### 23.9 数据 D9：958 条引用全部可定位

**推荐口述**：

> 这是 Q2 历史 99 次记录里，机器识别的引用标记总数 958，未解析为 0；其中 80 次 accepted 记录是 710 个标记。标记能回到 evidence 和保存来源，不表示 958 个独立事实都正确，也不表示来源可信度和语义支持达到 100%。

**D9-Q1：958 是去重的引用吗？**

不是，重复 E 编号多次出现按标记计数。去重 evidence 数、来源数、任务数都是别的指标。先讲计数单位，避免面试官把 958 误解成大型独立事实核验样本。

**D9-Q2：0 未解析是否代表完全没有遗漏？**

只能说明识别到的格式都能解析。没有引用的事实、未知标记样式、写错但未被 regex 捕获的引用可能不入分母。要进一步测试解析覆盖、缺引用率、范围匹配和来源可读性；不能把未检出当不存在。

**D9-Q3：可定位如何实现，不是模型自己说有来源吗？**

抽取 quote 逐字检查来源正文，保存偏移/段落或 PDF 页码；报告 E 标记查证据身份，再追 source_id 和版本。程序确定性检查证据存在，模型负责语义支持。来源网页后来失效时，保存正文仍可复查当时输入，但不等于在线链接永久有效。

**D9-Q4：0/958 可以推出未来错误率小于多少？**

如果 958 次为同分布独立检测，零失败的一侧 95% 上界为 `1-0.05^(1/958)≈0.3122%`，大样本约 3/n。这只是教学推导；标记共享任务/证据、规则固定且样本选择有限，不满足完全独立，因此不能拿来承诺未来故障率。程序契约与边界测试更有意义。

**D9-Q5：模型复制错误原文但 quote 真能找到呢？**

引用完整性成立，事实可靠性仍可能失败。需要区分复述来源与认定客观事实，核查发布者、时间、方法和冲突来源。高级多 Agent 并不会把低质量来源自动变成可靠证据。

**D9-Q6：子 Agent 的 E-001 与根任务 E-001 冲突怎么办？**

编号是任务局部身份，跨任务引用应带来源谱系和任务/版本身份，根任务重新登记并回补原始来源；不能全局按 E-001 字符串盲合并。当前代码有 source lineage 处理，但详细案例仍需打开产物逐层解释。

### 23.10 数据 D10：10 例无答案均正确拒答

**推荐口述**：

> 简单集里的 10 个选定无答案任务最终都给 unable，未以无依据的确定结论冒充成品。这个结果支持当前拒答机制在这些样本上有效；样本只有 10 题，不能推断任意任务都不会幻觉，也要防止有答案时过度拒答。

**D10-Q1：任务无答案还是模型不知道？**

这里是“给定资料不足以回答目标”，不等于世界上不存在答案。模型可能凭训练知识知道，但闭卷约束不允许冒充资料证据，所以应说明资料缺口。若用户授权联网，可尝试补来源，依然不能编造。

**D10-Q2：拒答怎样算正确？**

检查不只看 unable 标签，还要看未伪造核心答案、理由是否对应真正缺口、是否保留有据的部分，以及可答题有没有错误拒绝。只说“无法回答”再暗中给无据答案不能算正确拒答。

**D10-Q3：10/10 为什么不能说 100% 稳定？**

样本观察确为 100%，总体率不确定。教学 Wilson 下界约 72.2%；零失败精确单侧 95% 失败率上界约 25.9%，不是零。数据代表性和相关性会进一步影响推断。应该说“选定 10 题均正确”，不说“生产准确率 100%”。

**D10-Q4：如何在拒答和有条件建议之间平衡？**

核心问题无证据时拒绝确定结论；若材料足够支持条件化建议，则明确假设、范围和待核实信息。这是 coverage/risk 权衡，需要人工期望标注。不能靠出现“可能”两个字就把无据推荐变为合格。

**D10-Q5：怎么设计更多边界案例？**

后续可加入资料只有部分答案、相互冲突、日期过旧、数值条件缺失、否定表达和多来源共同才能作答的任务，同时配有答案反例。评价 false acceptance 与 false refusal，检查拒答理由，不只扩大不可答题分母。

### 23.11 所有数字共用的回答规则

先用一句话定单位：“这是任务级/查询级/引用对级/标记级/估算文本级指标。”再说数据、配置、对照与统计。遇到无法由证据证明的追问，直接说明没有测过，并给出实验设计。

你可以回答“不知道当前总体显著性”“没有真实缓存账单读数”“没有独立标注表”。然后指出已测范围和下一步如何测，比用术语把不确定性包起来更可信。

## 24. 简历六条技术点的扩展追问树

每条用“解决的问题→当前实现→为什么这样选→失败边界→替代方案”准备。下列方案讨论不是在建议本轮修改代码。

### 24.1 多 Agent 协作调度

**主回答**：统一请求与结构化计划决定协作方式，程序校验依赖/角色/预算，上层线程池按依赖波次调度，最终产物走研究审校。Agent 数量、深度、权限、开销受限制。LangGraph 主要提供通用 Agent Loop，不要把线程池调度讲成全部由图原生 Send 完成。

**扩展 A：DAG 与状态机有什么区别，为什么都存在？**

DAG 表达子任务前置依赖，通常不允许循环；状态机表达运行状态迁移，可以有循环，例如模型→工具→模型、草稿→审校→修订。它们解决不同问题：任务图决定谁先完成，状态机决定任务当前能做什么。依赖环应拒绝，而受限修订循环合理；两者都需要终止条件。

**扩展 B：多个 worker 同时修改状态怎么避免竞争？**

单个图字段用 reducer 指定合并；线程池结果可以由主线程收集；共享预算和队列用锁/事务；上下文身份用 ContextVar 并显式复制。Reducer 不是数据库锁，也不保证外部文件写入安全。要按共享对象逐个确定所有权，不能一句“用了 LangGraph 所以线程安全”结束。

**扩展 C：EventBus 为什么锁外调用订阅者？**

锁内只生成序号、保存历史并复制 handler 列表，锁外回调避免长回调占住内部锁或订阅者再次 publish 造成死锁。代价是跨线程回调可能交错、慢 handler 仍拖慢自身发布线程。若需要异步可靠交付，需独立队列、背压、重试、投递身份与持久化，不是当前总线已支持的特性。

**扩展 D：预算预留与实际成本不一致怎么办？**

预留是启动许可，实际成本响应后结算，差额释放或记入累计。用量未知不能当零处理；根预算不是银行账户的原子扣款。要防止父子调用重复统计，同时保留未知消耗和停止原因。费用表只作估算，不能承诺账单硬封顶。

**扩展 E：什么时候用 debate？怎样避免“两个幻觉投票”？**

只在真实证据冲突或重要决策有比较价值时使用。两边都需要引用可核查依据，裁决者对支持关系与缺口负责；多数意见不等于真。相同模型和相同资料有相关误差，增加角色不能创造独立证据。当前轻量辩论是策略，不是经过理论保证的决策机制。

### 24.2 技能扩展与按需加载

**主回答**：Skill 是可复用方法说明，不是事实库或任意代码。扫描元信息→路由→依赖激活→注入本轮提示→结束清理，支持摘要/正文/reference 三层 API。81.6% 只是一个命中全文的注入估算实验。

**扩展 A：Skill 和 system prompt 模板有何区别？**

普通模板固定在某个应用；Skill 将适用描述、方法、依赖、权限与参考资料做成可发现的独立文件，运行时按任务选取。它仍主要以 prompt 指令生效，框架带来的价值在发现、路由、生命周期、权限和可观测，而非某种新模型能力。

**扩展 B：依赖失败会发生什么？可以部分激活吗？**

缺失或循环依赖显式报错，不进入正常 running；Runtime 记录激活失败并处理本轮技能选择。当前激活与正文注入并不是一个包含所有资源的强事务；不要把它宣传为包管理器级的完整安装回滚。若引入代码资源，需更严格的激活原子性和清理设计。

**扩展 C：路由误选、模型输出不存在技能怎么办？**

注册表查身份，不存在不能正常注入；召回为空或不合适可 NO_SKILL，rerank 出错有兜底。需要注意当前解析有宽松匹配，不应声称所有候选集合约束均由严格 schema 强制。真正质量要测 top-k 召回、最终误选和 NO_SKILL，而不是从 token 节省推出选得正确。

**扩展 D：第三方 Skill 会不会越权？**

它是运行指令，应该只载入可信技能，并按声明收紧工具权限；外部正文不能获得任意工具或系统权限。references 读取也需路径与声明约束。当前不是经过隔离的第三方代码商店，不能宣称所有不可信技能安全执行。

**扩展 E：如何做 Skill 版本控制和热更新？**

当前是文件与显式 reload，运行状态由 manager 管理。可靠演进应为每次任务记录技能内容哈希/版本，在途任务用冻结副本，新任务才用新版本；删除已用文件时保留运行证据。这属于可改进设计，不把 reload 描述成无缝事务热部署。

### 24.3 跨会话记忆与上下文优化

**主回答**：工作、情景、语义三层组织不同寿命内容，组件检索支持 hashing/sqlite-vec、BM25 与遗忘衰减。但默认 AgentRuntime 是 JSON LongTermStore，user 注入默认关闭；74% 和 29pp 属组件/显式配置对照。

**扩展 A：为什么不用全部历史直接塞 prompt？**

上下文有限，全部历史会增加成本、噪声和过时冲突。短期保必要执行历史，长期只写适合复用内容，按 query 召回并保留来源。检索会漏，摘要会丢限定条件，所以压缩/召回不能替代原始记录保留与事实核验。

**扩展 B：记忆写入怎样避免模型自己制造“事实”？**

写入策略区分用户明确要求记住、来源明确知识和自动经验。事实要带来源/置信/版本，过期要显式处理。当前默认 Runtime 有明确记忆请求路径，不能称所有任务经历都自动高质量总结写入。知识可信与频繁访问是两回事。

**扩展 C：衰减为什么只删除情景、不删除语义？**

历史经历可能与旧任务相关，时间久后价值下降；事实只是没人查询，不代表失效。所以语义降权，失效通过过期/更正管理。该规则是可解释启发式，不能把 exp 曲线当事实正确性模型。

**扩展 D：索引和存储怎么保持一致？**

JSON 记录与 sqlite-vec 索引属于两种资产，当前组件写入两边、读取解析 ID；不是跨存储事务。需要考虑一边写成功、一边失败、重启重建、孤儿记录和 metadata 持久化。面试可以讨论按 source-of-truth 重建索引，但不要说已保证强一致。

**扩展 E：缓存友好和安全分层是否有冲突？**

静态规则在前、动态材料在后既利于结构稳定也能表达信任差别，但缓存目标不能把不可信资料升为系统指令。不同 Role 位置可能改变模型行为，应对任务质量和注入风险另测。真正限制副作用的是程序权限和审批。

### 24.4 全链路评测与迭代优化

**主回答**：组件、流程、真实业务分层；执行完成、预期行为、成品质量分开；Trace、usage 与独立评分可以定位问题。漂移与 A/B 有脚本支持，AutoOptimizer 是白名单规则建议、默认 dry-run，不是自动训练或自主线上调参。

**扩展 A：如何知道问题是代码还是模型？**

先查 request、资料状态、权限、预算和 stage 是否正确，再看格式解析与模型内容。无资料、错误 schema、取消状态都可能表现为模型失败。用可控桩复现机制，再用选定真实样本验证语义，不先到处改 prompt。

**扩展 B：为什么不同评测模型就叫独立？**

项目记录 model_name 不同是执行配置上的独立，不意味着统计误差独立。模型家族、训练资料和文风偏好都可相关，仍需盲评、人工抽检、固定标准。无实际配置证据时不能假定 Grader 一定换了模型。

**扩展 C：什么是轨迹评测，是否包括隐藏 Chain-of-Thought？**

检查外显调用轨迹：是否用了允许工具、是否重复失败、是否引用了原资料、预算何时停止、阶段是否跳过。它不需要也不声称保存隐藏推理。结果对而路径违规仍是问题，路径正常而答案错也要分开诊断。

**扩展 D：漂移阈值怎样设，怎么避免误报？**

先冻结同数据集、同模型和指标定义的基线，按方向和尺度设绝对/相对阈值，结合最小样本量与多批次趋势。数据换难度造成质量下降不等于程序退化；供应商模型变动也需版本记录。当前脚本阈值告警不自动知道根因。

**扩展 E：AutoOptimizer 为什么不直接应用？**

规则可能互相冲突：降低输出缓解延迟却增加截断，提高调用数减少半途停止却提高费用。默认 dry-run 让建议可审计，再在控制变量下验证，成功才变更配置。它不应绕过任务质量门槛。

### 24.5 引用可信度优化

**主回答**：先测可定位与语义支持的差距，再局部调整引用纪律和审校。单条证据只支持它对应的子句；报告必须区分事实、推断与缺口。当前 micro 改善有证据，覆盖和统计显著性边界也要说明。

**扩展 A：事实核查和蕴含判断有什么区别？**

蕴含问“给定证据是否能推出断言”，事实核查还问证据本身是否可靠/充分以及其他来源是否反驳。文本有句话不等于事实为真。例如广告资料称“最先进”，忠实引用也不能直接认定客观领先。当前支持率主要查前者。

**扩展 B：多个证据一起支持单句，应如何评？**

拆成可核查子命题，或评估证据集合能否共同支持结论。单对评分不能把合法多跳结论全部判错，但集合评审也不能让不相关证据凑数。当前优化主要对齐单对引用范围，多来源复杂句仍是明确边界。

**扩展 C：少引是否一定更好？**

不是。少引提高精确度可能降低覆盖；多引增加冗余也可能支持完整范围。目标是充分且准确的最小证据集合，不是引用数量最少。要联合评估覆盖、支持、必要事实和任务完成，而不是优化一个百分比。

**扩展 D：怎样处理矛盾来源？**

先检查是否同对象、同指标、同时间、同范围和同计量单位；不同条件的数字差异未必冲突。无法消解时保留并归属来源，说明不确定，不用多数票覆盖。当前已有冲突标准优化，但不能承诺能自动裁定一切事实冲突。

**扩展 E：为什么 prompt 修改不等于作弊？**

通用规则提高引用与断言对应关系可以是方法改进；泄漏具体答案、为某题写例外规则或只挑新输出则是污染。冻结规则后未见集验证、保留全部结果和失败，有助于区分。当前小留出集只提供有限证据，不宣称排除全部过拟合。

### 24.6 报告交付质量控制

**主回答**：程序检查引用和必要结构，模型查支持与遗漏，修订有限且版本化；等级与执行状态分离；无据时拒答，允许基于已有材料作有条件建议。禁语字面命中当前是 warn，而非任意词出现就硬拒收。

**扩展 A：为什么不能直接用 Reviewer 的分数决定？**

模型可能漏掉确定性错、偏爱自己的文风或格式；程序 error 必须拦截。模型又擅长程序难判断的语义，所以互补。链内 accepted 后仍可能被独立业务评审否决，这正是质量分层设计。

**扩展 B：最多两轮修订，会不会牺牲质量？**

会在复杂任务上保留草稿，但有限轮次避免无限循环和费用膨胀。应该交付明确局限，保留问题和用户可继续改稿的入口。若要调上限，需测质量收益/费用曲线，而不是默认越多越好。

**扩展 C：如何理解 accepted、draft、unable、failed？**

分别是链内成品、待完善、资料无法完成、阶段失败。completed/partial/cancelled 是执行状态，不是第五/第六质量等级。正确 unable 可以在拒答评测中成功，但不能当成完成用户所有目标。

**扩展 D：报告恢复会不会覆盖旧结果？**

版本化保存报告与审校，阶段先落产物再提交状态；恢复复用已提交资产，未知外部操作禁止自动重放。文件+SQLite 非一个事务，恢复仍需审计/对账。可以解释可用恢复，不说永不重复或任意字节断点。

**扩展 E：什么条件才可叫生产可用？**

要针对真实用户任务建立验收、风险与 SLA，完成权限隔离、凭据/日志保护、监控、故障恢复和部署验证。当前是签收过的本地个人平台，试用任务 AI 生成，部分组件未默认接入；不能借企业项目术语补齐不存在的生产证据。

## 25. 基础知识详解：统计、并发、检索、缓存与运行治理

本章从定义、公式/例子、与项目关系三个角度解释。公式用于理解，不要求在口述中背完整推导。新增区间和检验示例是本次教学计算，不是历史业务报告的既有结论。

### 25.1 总体、样本、观测单位与独立性

总体是希望结论适用的对象，例如未来复杂研究任务；样本是实际测试的任务。观测单位可以是任务、query、模型请求或引用对，单位不同分母就不同。

同一报告 20 个引用对通常相关，不能当 20 个独立研究任务。样本多但都来自相同主题也可能代表性弱。独立性指一个样本的结果不因共享机制强烈依赖另一结果；随机生成不同 ID 不会创造独立性。

项目：30 例是任务数，257 是引用对数，958 是可识别标记数，不能横向比较谁“样本更大因此质量更可信”。

### 25.2 比例、百分比、百分点与相对改进

比例 `p=k/n`。从 60% 到 75% 是 +15 个百分点，相对增长 `(75-60)/60=25%`。错误率从 40% 到 25% 的相对下降是 37.5%。同一变化可得到不同数，必须命名分母。

项目：前缀 +28.91pp，不是费用节省 28.91%；v3 严格支持从 69.48% 到 88.72% 约 +19.24pp，不是“任务成功增加 19%”。对齐案例、指标和版本后再谈改善。

### 25.3 均值、中位数、p95 与长尾

均值是总和/n；中位数把样本排序后取中间；p95 是约 95% 观察不超过的阈值，具体插值算法应说明。少数极慢样本会显著拉高均值，p95 描述尾部体验，不能仅用 p50 掩盖长尾。

例：耗时 1、1、1、1、16 秒，均值 4 秒、中位数 1 秒；典型快但尾部差。只有汇总均值和标准差不能准确重建分位数。

项目的 66.5% 报告有均值/中位数/标准差，没有原始时间数组，不能补编 p95。实际研究需要区分调用延迟、队列延迟和端到端时长。

### 25.4 方差、标准差与标准误

样本方差 `s²=Σ(x_i-mean)²/(n-1)`，标准差 s 描述单次观察波动；均值标准误在独立条件下约 `s/sqrt(n)`，描述均值估计的波动。二元比例标准误近似 `sqrt(p(1-p)/n)`。

标准差小不等于无偏，也不保证跨环境稳定。100 次相同有偏样本可有很小标准误，却仍偏离真实业务。

项目：桩时延小标准差说明实验简单；模型真实语义与服务延迟的方差需要新样本，不由这条数据推断。

### 25.5 置信区间的正确含义

频率学派区间是一个重复抽样程序：若假设成立且不断独立取样构区间，约 95% 的区间覆盖固定总体参数。它不是“95% 的任务正确”，也不是默认给固定参数一个贝叶斯概率。

区间只量化指定抽样模型的不确定性，不修正任务选择偏差、答案泄漏和错误标注。项目 74% 的区间仍只基于这 100 条构造 query。

### 25.6 Wilson 比例区间与样本量

普通 `p±1.96*SE` 在小样本或接近 0/1 时可能失真甚至越界。Wilson 使用 score 方法形成更合理的有界区间，教学计算可写成：

```text
denom = 1 + z²/n
center = (p + z²/(2n)) / denom
half = z * sqrt(p(1-p)/n + z²/(4n²)) / denom
interval = center ± half
```

独立二元假设下：74/100 约 [64.6%,81.6%]；29/30 约 [83.3%,99.4%]；17/20 约 [64.0%,94.8%]。这些是教学区间，尤其人工一致和引用对不一定满足抽样假设。

样本量近似与 `1/e²` 成正比，误差要求从±10pp 改为±5pp，需约四倍独立样本。官方概念参阅 [NIST 比例区间](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)。

### 25.7 零失败与 rule of three

若每次独立且失败概率 q 相同，n 次均未失败的概率为 `(1-q)^n`。令它等于 0.05，可得到单侧 95% 上界 `q=1-0.05^(1/n)`。

n 大时 `q≈-ln(0.05)/n≈3/n`。n=10 精确上界约 25.9%，3/n=30% 只是较粗近似；n=958 精确约 0.3122%。零失败不代表失败概率为零。

项目标记共享证据/报告且只计能识别的格式，这个独立模型不完全适用。该推导用来反驳“观察100%=永远100%”，不作未来故障率承诺。

### 25.8 Bootstrap、配对与聚类重采样

Bootstrap 从观测数据有放回抽样，计算统计量，多次形成经验分布。percentile 区间取分位点；其他如 BCa 会调整偏差/偏斜，不是本项目已实现方法。

独立 query 可重采 query；A/B 同题要同一个 task 索引一起抽，保持配对；引用对属于报告，要按报告/任务抽，再保留该任务内部对，避免假独立。更多 resamples 只稳定数值，不增加真实信息。

项目 memory 指标用 2000 次 query 重采样；支持率留出尚没有正式 cluster bootstrap 产物。算法概念可对照 [SciPy Bootstrap 文档](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats.bootstrap.html)，本项目不以 SciPy 为必需依赖。

### 25.9 假设检验、p 值、显著性与效应量

零假设通常是无差异，p 值描述在零假设及相应统计模型成立时，观察到至少同样极端统计量的概率。它不是零假设为真的概率，也不是方法有效概率。

显著性水平例如 0.05 是预先选择的决策阈值；统计显著不等于业务有价值。效应量给实际差异，例如延迟少多少秒、质量多多少pp。多次试不同参数挑显著结果会提高假阳性，需要预定义主要指标和复验。

项目不能因 `ExperimentRunner` 存在就宣称每个简历指标已显著；单轮、无原始样本的报告尤其需要克制。

### 25.10 Welch、配对 t、符号检验与置换

Welch 比较独立组均值且允许方差不等，标准误用 `sqrt(sA²/nA+sB²/nB)`，自由度用 Welch-Satterthwaite 近似。配对 t 先算每题差值，再检验差值均值；它也有分布条件。

符号检验只看正负，不看幅度：12 个无平局任务中 8 正 4 负，双侧 `2*P(Binomial(12,0.5)≥8)≈0.388`。置换检验在交换性条件下交换 A/B 或翻转差值符号，构造零差异分布。

这些不是随意替换的黑盒；按单位、独立性、配对和目标选择。正式概念见 [NIST 两样本比较](https://www.itl.nist.gov/div898/handbook/eda/section3/eda353.htm)。

### 25.11 Micro、Macro、加权与选择偏差

micro 把分子分母全汇总；macro 先每题算比率，再等权平均；weighted macro 用预定权重。若每题长度不同，micro 易被长题主导。

例：题 A 90/100，题 B 0/1。micro=90/101≈89.1%，macro=(90%+0%)/2=45%。两者都正确，代表不同目标。

项目留出 micro 60.1%→73.4%，macro 64.0%→72.7%。案例选择、失败被排除、输出长度改变和分类过滤均可影响读数，需保留全体与失效原因。

### 25.12 准确率、Precision、Recall、F1 与拒答

二分类有 TP/FP/FN/TN。Precision=TP/(TP+FP)，Recall=TP/(TP+FN)，F1 是两者调和平均；准确率=(TP+TN)/总量。哪一类为 positive 必须先定义。

拒答问题可设“资料可答”为 positive：正确作答是 TP，对不可答给答案是 FP，对可答拒绝是 FN。只看总体准确率会忽略错答风险和过度拒答。更细还要区分“尝试作答但内容错误”，不能用等级表替代答案正确性混淆矩阵。

项目 10/10 是不可答样本拒绝观察，19/20 是可答子集成品等级，尚不是完整语义分类矩阵。

### 25.13 Hit@k、MRR、Recall@k、nDCG

Hit@k 是每 query 是否至少一个指定相关结果；MRR 平均首个相关排名倒数；Recall@k 看召回相关占所有相关；nDCG 对相关等级和排名折扣，归一到理想排序。

如果一题多个相关记忆，只有一个指定 gold ID 会把其他正确知识误作未命中，应扩大相关性标注。项目当前单 ID 标注适合小型机制验证，不能等同全面检索评价。

### 25.14 观察一致率、Cohen's kappa 与校准

观察一致率 po=两标注者相同标签数/n。kappa=`(po-pe)/(1-pe)`，pe 由两者标签边际频率估计机会一致。标签极不平衡时，po 高而 kappa 可能低。

没有完整双标签不能反推 pe。概率校准则是预测 0.8 的事件长期是否约80%发生，和两个人标签一致不是同一概念。项目“人工校准”主要指抽检语义标准，不意味着模型概率 calibration 已测量。

### 25.15 消融、泄漏、过拟合与留出

消融移除某组件衡量贡献，例如同条件去 BM25/去 decay。改变多个变量无法唯一归因。泄漏指执行模型获得本应只供评分的信息；过拟合指针对已看案例反复调整导致对新案例效果不稳。

留出必须规则冻结后测试，不能继续依它调规则还反复称未见。项目级未见不保证基础模型预训练无污染。跨语言、多来源、干扰量一起变化需分层设计，不简单定因。

### 25.16 并发、并行、I/O 与 GIL

并发是多个任务重叠推进；并行是同一时刻实际执行。单线程事件循环可 I/O 并发，多核进程可 CPU 并行。线程池的价值在同步 I/O 重叠，不要求 Python 字节码多核并行。

常规 CPython GIL 限制字节码同时执行，I/O 等待和部分原生库可释放它；自由线程构建另有条件。锁仍可能需要，因为共享业务不变量不靠 GIL 自动保证。参考 [Python 3.14 threading](https://docs.python.org/3.14/library/threading.html)。

### 25.17 Future、线程局部与 ContextVar

Future 表示未完成的结果，可读取返回/异常；超时是停止等待，不自动停止后台函数。取消通常只阻止尚未开始的任务。

thread-local 按 OS 线程保存，ContextVar 按上下文保存；线程池复用线程时不能依赖隐式身份。`copy_context` 复制上下文绑定，但对象引用可能仍指同一个 ledger，因此还要锁，不能说复制后数据完全隔离。

项目为每次 submit 复制上下文，用来保留任务/角色身份，不提供进程之间上下文传输。

### 25.18 依赖关键路径、Amdahl 与背压

任务 DAG 总时长受关键路径下界和资源数量限制。增加线程无法压缩必需串行依赖；Amdahl `S=1/((1-f)+f/P)` 假定可并行部分理想加速，不包含限流和负载不均。

背压让生产任务速度不超过消费者承受能力，防队列无限增长；限制并发不等于限制排队长度。项目有任务与预算上限，但不是完整分布式背压系统。

### 25.19 向量、点积、余弦与欧氏距离

向量是一组数，点积 `Σxi*yi`；余弦为点积除两个模长，衡量方向相似；L2 是差向量长度。归一化单位向量时余弦=点积，且 `cos=1-L2²/2`。

不同距离的好坏方向不同，融合前要统一。零向量需要单独处理。项目256维哈希计数有碰撞和词面局限，索引类型不决定语义质量。

### 25.20 TF、IDF、BM25 与长度归一

TF 是词频，IDF 将常见词降权、稀有词提高判别力。BM25 的词频饱和避免一个词重复无穷增分；b 调文档长度归一，k1 调饱和程度。

项目用候选集内 IDF、最大分归一与0.5权重。候选变化会改变归一和排序，权重是启发式配置，不是训练出来的最优参数。BM25 重排不能找回前层完全没召回的文档。

### 25.21 哈希嵌入、神经 embedding、ANN 与融合

哈希嵌入把词映射到维度，确定、便宜但语义弱。神经 embedding 将文本编码为学习到的表示，可捕捉同义语义但需模型、版本和成本管理。

向量数据库/扩展负责存取与检索，不等于嵌入模型。精确检索与近似 ANN 的召回/速度不同；当前项目不宣称已有 HNSW 等特定 ANN。

混合检索可以词面和向量独立召回取并集，再融合；RRF 用 `Σ1/(常数+rank)` 合排名，减少分数尺度依赖。项目当前是向量过召回后 BM25 重排，不是已采用 RRF 的双路系统。

### 25.22 Token、上下文长度与自回归生成

Token 是模型词表单元，不等于字或词。BPE/类似分词方法把常见子串组合成 token，同一文本不同 tokenizer 可不同计数。输入上下文和生成输出都占模型长度/费用，但预算字段可能分别限制。

自回归生成逐步依据前文预测下一个 token，工具调用也是一种结构化输出，实际动作由宿主执行。格式合法不保证事实正确；temperature=0 也不保证跨服务版本永远一致。

项目累计输出上限与单次 Adapter max_tokens 不同，隐式 thinking 可能计入 completion。估算 token 不能精确代表账单。

### 25.23 Attention、KV cache、前缀复用与答案缓存

Attention 让当前位置参考先前表示；生成时保存先前 token 的 key/value，避免每一步从头重算历史，称 KV cache。服务端若支持跨请求共享相同输入前缀计算，可以减少重复 prefill。

这是计算复用，不是自动复用上次答案。应用结果缓存直接返回旧结果，需任务身份和时效。项目29pp只测完整相同消息的代理，不含服务端实际 key、TTL、匹配粒度和缓存调度，不能推出具体速度/费用。

### 25.24 RAG、Agentic RAG、来源与证据

RAG 是生成前/中从外部资料检索相关上下文；Agentic RAG 加入由模型或策略决定检索、改写、工具和反思。更多循环需要预算与终止约束。

研究平台的资料导入、证据抽取、写作与审校是业务链；不能凭这些词就声称实现了企业知识库的神经分块/混合搜索/reranker。来源是材料，证据是定位摘录，断言是报告命题，分别需检查。

### 25.25 蕴含、部分支持、矛盾与未知

蕴含要求证据在相同条件下支持断言；partial 只覆盖部分；矛盾是同条件下相反；unknown 是材料不能决定。时间、样本、数量、因果和条件扩展都是常见越界。

例：“试点40人中30满意”支持试点75%，不支持全国75%；“销量和投放一起增长”不直接证明投放造成销量增长。项目程序只能验证 quote 存在，语义 Judge 判支持，来源真实性另查。

### 25.26 State、Reducer、DAG 与状态机

State 是明确数据；Node 返回局部更新；Reducer 决定累积或覆盖；Edge 决定下一步。DAG 排依赖，状态机控迁移。默认 append reducer 可能重复追加，按ID合并是不同策略。

图逻辑决定执行，不自动提供外部事务、幂等和安全。项目大文件和研究阶段在文件/SQLite 中，不应把所有能力归因 LangGraph。

### 25.27 事务、ACID、WAL 与跨存储一致性

原子性是事务内全做或全不做；一致性是不变量成立；隔离性控制并发干扰；持久性指提交后的保存保证，具体依实现/配置。WAL 将变更先写日志，有利于读写并存但SQLite仍主要单写者。

一个数据库事务不能直接包住模型请求、文件写入和远程副作用。长事务持锁会影响吞吐；应明确提交边界并对账。项目先写产物后记状态，具备崩溃窗口，恢复需审计。

### 25.28 租约、幂等、重试与 exactly-once

租约是暂时执行所有权，心跳延长；租约过期不证明旧 worker 已物理停止。幂等表示重复同动作不会新增副作用，需要定义请求身份与版本。

至少一次投递可能重复，至多一次可能丢动作；外部 exactly-once 需要跨系统协调或对方幂等支持，不能由本地标志保证。项目 succeeded回放、unknown不重放是保守恢复，不是严格一次执行证明。

### 25.29 超时、取消、熔断与预算

超时是等待期限，取消是请求停止，熔断是连续失败后暂拒请求，预算是累计资源限制。四者都不能自动撤销已产生副作用。

当前 IterationBudget 状态 closed/open/half_open，试探由调用方触发；金额账本另算。工具线程 timeout后台可继续，按side_effect控制重试。不把这几种机制写成万能故障恢复。

### 25.30 JSON Schema、JSON-RPC、MCP 与 A2A

JSON 是数据格式，Schema 约束结构和类型；JSON-RPC 用 method/params/id 关联请求和响应；MCP 约定工具等能力交互；A2A 讨论 Agent 之间协议协作。

Tool Calling 是模型提出调用，MCP 是宿主与外部工具服务交互，两者不是替代关系。项目 Schema 是子集、MCP 是历史版本的本地工具适配，不宣称最新协议全部能力或完整 A2A 网络。

### 25.31 权限、最小授权与 Prompt Injection

模型能生成工具名不代表有权限；实际授权是程序集合/审批。子权限取父和角色集合的交集，不能因提示词“我是管理员”扩大。

Prompt Injection 是不可信资料尝试改变任务/规则。Role/分隔符帮助表达边界但不是可靠沙箱；工具 allowlist、审批、路径/网络检查限制后果。Skills与来源内容信任等级不同，不能自动把网页里的“指令”执行。

### 25.32 SSRF、DNS Rebinding、路径逃逸与 XSS

SSRF 让服务端访问攻击者指定内网等地址；防线是协议、解析IP、危险网段和逐跳重定向检查，连接固定到验证IP减少重新解析窗口。不是只拒绝字符串 localhost。

路径逃逸用 ../、绝对路径或链接越过受控目录，应规范化后检查物理包含关系。XSS 是资料被当可执行 HTML/JS，工作台用文本DOM显示动态内容；只读材料也可能影响渲染安全。

项目这些措施适合本地边界，不等于完整公网、多租户和第三方代码隔离。

## 26. 模拟面试：从数字追到架构和实验设计

练习方法：先盖住答案，用自己的话讲；对方每一轮都追问上一轮里的名词。讲到不会的地方，记录需要打开的代码或证据，不能只背一段更长的回答。

### 26.1 场景一：面试官怀疑 66.5% 只是 sleep 演示

**面试官 1：66.5% 是怎么测的？**

候选人：“6 个独立子任务、3 并发、每题0.15秒等待桩、50轮，顺序0.902秒、并行0.302秒。各轮下降比例均值66.5%。我把它限定为并发机制收益，没有真实模型全链提速数据。”

**面试官 2：那不是谁开线程都能实现，项目价值在哪？**

候选人：“单纯等待并行并不复杂，这个数字只是机制验证。项目需要同时满足依赖、预算、权限和交付：独立任务才并行，每个子任务预留额度和收紧权限，失败不能静默丢弃，合并结果仍走证据与审校。因此我更愿意展示完整任务的计划、账本和产物，而不是把这个百分比当核心质量贡献。”

**面试官 3：你说依赖，怎么判断哪几个能同时跑？**

候选人：“执行方案每题有 depends_on，先检查引用节点存在和无循环。ready 只包含未完成且前置条件满足的任务，按资源上限形成波次。A/B/C→D 时前三能同波，D等它们的结果。前置失败要明确降级、停止或重规划，不能假装全图完成。”

**面试官 4：共享预算锁会不会把并发串行化？**

候选人：“这是要按实际接线分析的点。当前 JobLedger.call 在锁范围做调用，不能承诺同一账本下所有请求并行。应用层子任务使用各自执行账本，先在根预留，完成后结算。要讲真实并发路径，不能只看到ThreadPoolExecutor就忽略下层锁；如果后续优化，需保持预留/结算不变量再减少锁内阻塞。”

**面试官 5：如果需要CPU计算，线程池还有效吗？**

候选人：“常规GIL构建对CPU密集Python字节码不一定多核加速，需要进程或释放GIL的原生库；模型HTTP等I/O等待适合线程。当前sleep指标不证明CPU能力。工具类型不同，执行方式和取消隔离策略也应不同。”

**面试官 6：你若测真实提速，如何公平？**

候选人：“同模型、同子任务图、同输入和质量门槛，计入调度、汇总与审校，按题多轮随机化先后。记录失败和重试，不只保留成功样本；同时报告p50/p95、质量、费用与配对差异。这个实验我目前没有完成，所以不报预计三倍为实测。”

**练习检查**：没有回避桩实验；能讲价值超出线程；准确指出锁边界；没有凭空增加真实性能证据。

### 26.2 场景二：从 88.7% 追到“少说少错”和统计显著性

**面试官 1：你从66%提升到88.7%，为什么？**

候选人：“先纠正口径：66%是34任务混合集，88.7%是30题v3，不能直接同范围对比。当前旧缓存限定v3后约69.5%，到88.7%约+19.2pp。方法是拆复合断言、引用贴近支持子句、缺口不挂不当引用，审校对应查支持范围。”

**面试官 2：分母变小，是否删除了难内容？**

候选人：“对数从426到257，确实有这个风险。优化减少冗余和复合引用会减少对数，但仅比例变好不够。我会联合看必要事实覆盖、任务符合、未引用断言和报告长度。没有完整覆盖读数，就不能声称全部事实正确性提高同样幅度。”

**面试官 3：你怎么算 supported？**

候选人：“先解析报告带引用单元，再按E编号找到quote，独立评审模型对每个unit—quote判supported/partial/unsupported/unrelated。strict只计supported，宽口径加partial。它不是每条独立事实，也不判来源客观真伪；多跳集合支持是当前单对测量的边界。”

**面试官 4：模型judge凭什么可信，85%人工一致在哪？**

候选人：“不同评审模型降低同一模型自评偏差，但不保证客观。现有日志写17/20一致，我没有找到独立逐条标注表，所以不能拿它硬背书。若实际没有本人独立标注依据，我会删去简历85%。应该留盲标、标签标准、分歧和裁决记录。”

**面试官 5：12个留出题是否证明泛化？**

候选人：“它只给方向性证据。micro60.1到73.4，macro64.0到72.7，12题里8升4降，单轮。两分组均值提升但不是每题无退化，也不能排除数据选择和模型预训练污染。”

**面试官 6：那显著吗？**

候选人：“当前未做正式多轮任务级推断。只按8升4降的符号做教学双侧检验，p约0.388，不够常用显著性。这个检验不看幅度，所以也不能反过来说方法毫无效果。下一步按任务配对、多轮，做差值区间和覆盖评估，不把338个相关引用对当338个独立任务。”

**面试官 7：如果 95% 门槛没过，项目为什么可以签收？**

候选人：“需要分清当时验收标准、宽/严格指标和用户接受的已知限制。简单集宽口径96.5，严格88.7，复杂多来源更低；签收不等于所有指标普遍生产达标。应说明已知质量边界，并避免简历写全面解决引用幻觉。”

**面试官 8：如果你重新写简历，如何描述？**

候选人：“我会写实现断言—证据支持评估与引用纪律优化；简单30题严格支持率88.7%，12题留出配对整体60.1到73.4，并保留样本与单轮范围。删掉跨混合集起点和没有人工证据的数字。”

**练习检查**：先纠正分母；识别覆盖风险；区分strict/lenient；没有用“独立”掩盖judge偏差；会解释不显著与无效果的差别。

### 26.3 场景三：74% 记忆命中追到基础检索和默认接入

**面试官 1：你的74%是什么？**

候选人：“100条构造改述query，指定正确记忆ID在前三算命中，74条命中；Top-1是60。用哈希向量+BM25+衰减，历史sqlite-vec后端。是组件Hit@3，不是答案正确率。”

**练习检查**：区分向量索引和embedding；能说出BM25数学意义；不掩盖默认接入；知道重采样不增加样本；改进路线先诊断后修改。

### 27.2 只读教学计算与任务级复核

本段读已保存JSON并做数学运算，不导入项目模型配置，不发模型请求，不保存或覆盖报告。区间是教学，不当业务验收。

```python
import json
import math
from pathlib import Path

root = Path("eval/reports")

def read_report(name):
    return json.loads((root / name / "support_rate_report.json")
                      .read_text(encoding="utf-8"))

def case_rates(report):
    # 直接从原始 pairs/verdicts 分组，不平均已四舍五入的 case_rate
    counts = {}
    for pair in report["pairs"]:
        verdict = report["verdicts"].get(pair["id"])
        if verdict is None:
            continue
        bucket = counts.setdefault(pair["case_id"], [0, 0])
        bucket[1] += 1
        bucket[0] += verdict["verdict"] == "supported"
    return {key: yes / total for key, (yes, total) in counts.items()}

old = case_rates(read_report("support_rate_v3b_old"))
new = case_rates(read_report("support_rate_v3b_new"))
assert old.keys() == new.keys()
changes = [new[key] - old[key] for key in old]
print("tasks", len(changes))
print("macro old", sum(old.values()) / len(old))
print("macro new", sum(new.values()) / len(new))
print("up/down/tie", sum(x > 0 for x in changes),
      sum(x < 0 for x in changes), sum(x == 0 for x in changes))

def wilson(successes, total, z=1.95996398454):
    assert 0 <= successes <= total and total > 0
    p = successes / total
    denom = 1 + z * z / total
    center = (p + z * z / (2 * total)) / denom
    half = z * math.sqrt(p * (1 - p) / total
                         + z * z / (4 * total * total)) / denom
    return center - half, center + half

for yes, total in ((74, 100), (29, 30), (17, 20), (10, 10)):
    print("teaching Wilson", yes, total, wilson(yes, total))
for total in (10, 958):
    print("teaching zero-fail upper95", total,
          1 - 0.05 ** (1 / total))

# 同题提升符号：该教学检验不使用变化幅度
wins = sum(x > 0 for x in changes)
losses = sum(x < 0 for x in changes)
n = wins + losses
assert n > 0
tail = sum(math.comb(n, k) for k in range(max(wins, losses), n + 1)) / 2 ** n
print("teaching sign-test p", min(1.0, 2 * tail))
```

当前应输出12题、macro约0.63985/0.72687、8升4降0平、符号检验约0.38770。若未来产物换版，先确认数据身份，不继续引用旧值。

- **本次只读重算**：同v3基线296/426、留出macro和8升4降、Q2引用子集；没有新模型输出。
- **教学推导**：Wilson、零失败上界、8比4符号检验；基于假设帮助理解不确定性，不是历史已验收的统计结论。
