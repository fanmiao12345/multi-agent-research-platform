## 1. 目标用户流程

用户视角默认只有两步——**一次输入，一次拿结果**；中间过程系统自理，不打扰用户：

1. **输入（唯一必做的一步）**：研究主题（必填）；可选：资料文件/链接/粘贴文本、读者与长度要求、是否允许联网、预算与时限。预算有默认上限，可改。
2. **系统自理（用户无需参与）**：读题选型 → 按方案派工 → 子智能体研究/写作 → 汇总 → 成稿 → 审核 → 不达标返工。进度树与过程记录照常落盘，但是"点开才看"的备查详情，不是用户要盯的界面。
3. **只在两种情况才停下问用户**：① 方案预计花费超过钱闸阈值（默认值草案：模式目录最省与最贵典型成本取中点，数值待实测校准，用户显式预算优先，见 2.D）；② 关键业务条件不明（判定清单待定，首版仅"缺了就无法执行"的最小保守清单，见 2.D）。其余情况直接执行，不为表达偏好打断用户。
4. **交付（默认界面）**：结果报告（带 `[E-编号]` 引用）+ 一段**方式告知**——本次选了什么研究方式、一句话为什么、花了多少钱/多少次调用、交付等级（成品/草稿/无法完成）。详细过程记录（方案原文、实际派工、逐项花费、失败与重试）作为附件，想查再点开。
5. **可选开关**：「先看计划再开跑」（默认关）——打开后改为展示方案与预计花费、用户点"开始"才执行；适合首次使用或不放心的用户。

## 2. 能力分解

### A. 调度智能体（读题选型）

- 输入：主题、可用资料概况（来源数量/类型/是否可联网，**不含资料全文**——缩小提示注入面，资料内容一律不作为指令）、用户约束（预算/时限/读者/长度）、**任务硬约束（必需章节/禁止表述/关键事实，沿用 S6-05 契约）**、可用模式目录与各模式的能力边界。
- 输出：**结构化执行方案**（JSON，见第 3 节），必须包含：所选模式、选择理由、子任务清单（描述/角色/依赖/是否并行、**覆盖哪些必需章节**）、是否需要独立审核、预算与并发上限建议、预计调用数与花费、以及"降级预案"（首选模式失败或超预算时退到哪种更省的模式）。
- 约束：一次调用完成（失败重试一次）；本次调用计入根任务账本，purpose 记为 `orchestration_plan`；选型不得指定未注册的模式或角色；不得把预算上限调高；**每条必需章节必须至少被一个子任务覆盖（程序校验）**——缺映射即拒绝并重出一次，仍失败降级 fixed（fixed 链已有提纲补入兜底）。
- 失败处理：选型解析失败 → 退化为固定流程（已知最稳的一条），并如实记录"选型失败"。

### B. 执行器（按方案执行）

按方案把控制权交给对应策略实现，复用现有 `src/orchestration/*`，并补齐与研究写作的衔接：

| 模式 | 适用主题 | 现状 | 需要的改造 |
|---|---|---|---|
| single（单智能体） | 简单问答/单点整理 | 已有 | 作为最终"写作+审核"的执行体 |
| fixed（固定流程） | 结构清晰的整理/成稿任务 | 已有（`ResearchApplication` research 流程） | 作为候选模式与保底模式 |
| manager_worker | 需要先规划再派活的复杂主题 | 已有 | 子任务产出需落证据与产物，而非只回文本 |
| fanout | 多个互相独立的子题（可并行） | 已有 | 同上 + 并发与预算护栏 |
| dynamic_team | 复杂、需要边做边调整的主题 | 已有（含一次重规划） | 同上 + 每轮计划可审计 |
| debate | 有争议、需要正反论证的主题 | 已有（Debate-lite） | 产出需转化为可核查论据与结论，不是对话记录 |

**首版范围收敛（2026-09-10 审阅后定）**：auto 第一版只在 `fixed` 与 `fanout` 之间选型，先跑通"自动选型 → 实际执行 → 证据汇总 → 成稿审校"完整闭环并过离线与浏览器验收；`manager_worker / debate / dynamic_team` 与嵌套派生**逐个**走同款小批对比验收，验收一个开放一个（目录保留名称但不可选）。**候选按实际能力过滤**：方案只能选当前能力满足的模式（如任务需要外部资料而搜索不可用时，需检索的模式不进候选），不是看到模式名就允许选。single 暂不入首版目录（单点任务由 fixed 覆盖）。

**中途失败语义（auto 模式）**：单个子任务失败先原地重试一次（带副作用工具不自动重试，沿用现有规则）→ 仍失败由父任务重规划一次 → 再失败**不静默跳过**，按现有交付分级（draft/failed）收尾。每次重试与重规划都记账留痕，写进研究过程记录。

### C. 质量与证据（硬要求）

任何模式都不得绕过交付标准：

1. 子智能体的产出必须带**来源与定位**（来源 id、原文摘录、字符/段落位置），不得只回一段总结。
2. 最终报告必须由**成稿 + 审核**通道产出（现有写作与审校能力），多智能体负责"研究得更全"，不负责"跳过审校直接交付"。
3. 报告仍需满足任务硬要求（必需章节、禁止表述、关键事实），由程序层复验。
4. 交付分级仍为 成品/草稿/无法完成，与案例预期比对后判定，不允许用"步骤都跑完了"充当成功。

### D. 护栏、账本与可观测

- **预算（整任务分配得下，不只单子任务有上限）**：所有子智能体共享根任务账本，逐调用记账（purpose/角色/父子关系可追）；超限即停并保留已完成部分。**分配公式（2026-09-10 审阅后明确）**：可派工预算 ＝ 根任务剩余额度 − 在途调用预留 − 最终成稿与审校预留——先给最终交付留额度，再分给子任务；单子任务 ≤ 可派工预算的 40%，且 Σ(子任务额度) + 在途 + 预留 ≤ 根剩余（防止"三个分支各按同一时刻余额分 40%，合计 120%"）。调度模型可以建议预算，**程序负责核验与扣减**。成本区间必须基于同一任务规模与资料规模估算，不得拿简单问答与复杂研究的成本直接取中点。
- **并行前置（如实限制）**：当前根账本在模型请求期间持有同一把锁（`src/harness/model_gateway.py` 的 `call()` 全程持锁），同根任务的模型调用实际**串行**；不能凭 fanout 开了线程就宣称缩短模型执行时间。开放并行前必须先落地"额度预留（请求发起前冻结）→ 返回后结算/释放"并评估锁粒度（S8-03），否则 fanout"更快"不成立。
- **恢复承诺（可验证口径）**：原表述"恢复不重复付费"过强，改为——已提交的阶段产物优先复用；对结果或用量不确定的调用（请求已发出、本地未保存响应）单独标记，**不自动当作未执行重放**；确需重试时记录为新尝试与可能重复的费用。与"未知用量不记零"同一原则，并写成故障测试（见 8.A）。
- **并发**：默认最多 3 个并行分支（沿用现有 `max_parallel=3`；实际并行收益受上行锁限制约束）。
- **递归**：见第 5 节。
- **可观测**：页面上以树形展示"根任务 → 计划 → 子智能体 → 阶段 → 产物"；每个节点可见状态、耗时、花费、失败原因。
- **取消/恢复**：取消传播到所有在跑的子智能体；每个子智能体在阶段边界收敛；恢复时复用已完成子智能体的产物，不重复花钱（沿用检查点机制）。
- **计划确认**：默认自动执行；「先看计划再开跑」开关与"超钱闸/关键条件不明必须停"两种确认都复用 S4 持久化审批通道（绑定 job、落 state.sqlite，服务重启不丢）。
- **钱闸默认值（折中规则，数值待测试校准）**：模式目录为每个模式标"典型成本区间"；自动执行的默认阈值 = 最省模式典型成本与最贵模式典型成本的**中点**（2026-09-10 用户决定的折中规则）。预计花费 ≤ 阈值直接执行，超过则停下确认；用户显式设置的预算上限始终优先于默认阈值。默认数值先按本地估算表拟定，S8-05 跑出各模式真实成本分布后校准。**口径约束：区间必须基于同一任务规模与资料规模**（简单问答与复杂研究不可混算）。
- **关键条件判定清单（待定）**：「关键业务条件不明」的具体清单暂不确定（2026-09-10 用户确认）。首版只实现**最小保守清单**——仅"缺了就无法执行"的问题（如产品计划所举"比较哪两个对象"），其余一律采用可见默认值，不打扰用户；清单随试用反馈逐步扩充，每次扩充在 IMPLEMENTATION_LOG 记录理由。

### E. 搜索能力前置（"只给主题"的先决条件，2026-09-10 增）

S8 的目标输入可以只有研究主题，但**用户给链接 ≠ 系统自己找资料**，是两项能力；当前搜索网关仍是空占位（`src/harness/ingest/search.py` 的 `SUPPORTED_PROVIDERS` 为空）。主题研究试用前必须接通一个真实搜索服务，并按三档行为执行：

| 场景 | 系统行为 |
|---|---|
| 用户提供了资料 | 只用给定资料整理写作；发现缺口明确说明 |
| 无资料、允许联网、搜索可用 | 拆检索问题 → 搜索候选 → 读取原文 → 去重筛选 → 提取证据 |
| 无资料、搜索不可用 | 明确告知缺少资料，**不生成貌似经过研究的报告** |

**接入与使用规则**：

- 搜索摘要只用于筛选"值得读哪些网页"；具体数字、日期、条款、重要结论必须**读原文**并保存出处；正文读取失败记"正文读取失败"，不算已核实材料。
- 同文转载按 URL + 正文去重，不算多份独立证据（沿用 B3 去重）。
- 任务级搜索预算（首版草案，实测后校准）：第一轮 2～4 个检索问题、每问题 5～10 条候选、按相关性选读正文、第二轮只补未解决的问题；整任务的搜索次数/正文读取数/耗时/费用统一限额，多个子任务不得重复搜同一问题。达到资料覆盖即停；预算用完而证据仍不足 → 交付带明确缺口的草稿。
- 调度智能体的输入"资料概况"增加"搜索是否可用"字段，用于按能力过滤候选模式（见 2.B）。

**接入节奏（2026-09-10 用户决定：模拟先行，真实接入推迟到真正需要时）**：

1. **第一步·模拟搜索**：在现有搜索网关后实现**显式标记的 Mock provider**（`SUPPORTED_PROVIDERS` 增加 `mock`，仅 Mock/离线模式可选；真实模式绝不回退到 Mock，延续"不假装搜过"红线）。用于打通"拆检索问题 → 搜索 → 读原文 → 去重 → 证据"链路、能力过滤逻辑、搜索记账与三档行为的离线测试——这些逻辑不依赖真实服务商。
2. **第二步·真实接入（按需触发）**：主题研究试用真正需要联网资料时再接，**免费额度起步**（Google CSE / Tavily 优先评估，中文主力需求再上百度千帆/博查），接入前按官网核验接口与费用（S2-04）。验收标准不变：**输入一个主题，系统能找到相关原文、写出引用可核对的报告、并明确标出资料不足之处**。
3. 评测纪律：Mock 搜索结果只能进离线开发/评测，产物必须带"模拟搜索"标记，不得当真实研究证据展示或统计。

## 3. 调度智能体的输出契约（草案）

```json
{
  "schema_version": "1",
  "mode": "fanout",
  "reason": "主题包含 4 个相对独立的子问题，且资料充足；并行可在同等预算下更快完成",
  "complexity_signals": {"independent_subtopics": 4, "needs_planning_first": false, "controversial": false, "material_ready": true},
  "subtasks": [
    {"id": "T1", "role": "researcher", "description": "收集子题一的事实与来源", "depends_on": [], "parallel": true, "covers_sections": []},
    {"id": "T2", "role": "researcher", "description": "收集子题二的事实与来源", "depends_on": [], "parallel": true, "covers_sections": []},
    {"id": "T3", "role": "writer", "description": "按收集结果写初稿", "depends_on": ["T1", "T2"], "parallel": false, "covers_sections": ["资料目录", "覆盖范围"]},
    {"id": "T4", "role": "editor", "description": "独立审核并指出无依据表述", "depends_on": ["T3"], "parallel": false, "covers_sections": []}
  ],
  "needs_reviewer": true,
  "max_parallel": 3,
  "budget": {"max_calls": 40, "max_cost_usd": 0.30, "max_seconds": 900},
  "fallback_mode": "fixed",
  "expected": {"calls": 18, "cost_usd": 0.12, "seconds": 420}
}
```

规则：

- `mode` 只能取已注册模式；`role` 只能取现有角色档案；`subtasks` 数量设上限（草案 ≤12）。
- `budget` 不得超过用户/系统给定上限；执行器按实际值取最小值。
- `fallback_mode` 必填（默认 `fixed`）。
- 契约版本化（`schema_version`），解析失败即降级，不猜测。
- `covers_sections`：子任务与必需章节的映射，程序校验每条必需章节至少被覆盖一次（见 2.A）。
- `complexity_signals`：选型判据的结构化读数，用于程序核验"理由是否与输入一致"（如 `independent_subtopics` 对照主题与资料概况抽查），并进入研究过程记录。

## 4. 模式选择判据（写进调度提示词，作为可审计依据）

- 主题是否包含**多个互相独立**的子问题 → 考虑 fanout / manager_worker。
- 是否需要**先规划再执行**、子任务之间有依赖 → manager_worker / dynamic_team。
- 是否存在**争议性结论**且需要正反论证 → debate（并必须要求论据可核查）。
- 是否只是**单点整理/成稿**、资料已齐 → single / fixed（更省钱、更稳）。
- 是否**边做边可能发现新问题**、需要重规划 → dynamic_team。
- **默认取"够用的最省模式"**：能用 single/fixed 解决就不上多智能体；多智能体只在质量或时间上有明确收益时使用，并在方案里写明理由。

## 5. 子智能体规则（含嵌套护栏）

用户已确认允许"子智能体再派子智能体"，因此必须给出硬护栏：

1. **深度上限**：默认 2 层（根 → 子 → 孙）；超过即拒绝派生并记警告。
2. **预算继承且递减**：子智能体预算 = 父任务剩余预算的一部分（草案：不超过父预算的 40%）；任何一层都不得突破根任务上限。
3. **数量上限**：整个根任务派生总数上限（草案 ≤12，**含方案子任务与嵌套派生合计**），单层并发 ≤3。
4. **同题去重**：同一子任务描述不得重复派生（归一后比对），避免自激循环。
5. **角色白名单**：现有 `researcher / organizer / writer / editor / agent`；不支持的角色直接拒绝。
6. **记账与追溯**：每个子智能体是一个独立 run，记录父 run、角色、purpose、耗时与花费。
7. **取消与失败传播**：父任务取消 → 所有子智能体在阶段边界收敛；子智能体失败不静默（记失败原因，父任务可重规划或降级）。
8. **工具与权限最小化**：子智能体的工具集不得超过父任务允许范围（沿用现有权限交集规则）。

## 8. 验收口径（怎么算成功）

分三层，缺一层都不算通过：

**A. 功能与护栏（离线可验收）**

- 给定主题能稳定产出合法方案；非法模式/角色/超预算的方案被拒绝并降级。
- 选中的模式**确实被执行**（日志与产物可证），子智能体可追溯到父任务与角色。
- 递归深度、数量、并发、去重、预算递减、取消传播全部有测试；任何一层超限都有明确拒绝记录。
- 预算账本：所有子智能体调用都计入根账本，未知用量不记零；调度调用本身也单独可见（purpose=orchestration_plan）。
- 方案稳定性：同一主题同输入，桩大脑下确定性可复现；真实模式采样 3 次，记录模式选择一致率（波动本身进报告，不预设 100%）。
- 产品体验（用户视角）：一次输入拿到结果，中途零打扰（除"超预算阈值/关键条件不明"两种必须停机确认外）；交付默认带方式告知；进度树/过程记录是备查详情而非必经界面。
- 取消与恢复：子智能体在边界收敛；恢复优先复用已提交阶段产物，**不确定调用单独标记、不自动重放**（可验证承诺，见 2.D），重复费用风险有故障测试覆盖。
- 指标分离（2026-09-10 审阅后明确）：执行完成率（流程正常结束）、预期行为符合率（应成品/草稿/无法完成时处理正确）、成品质量达标率（事实/引用/完整性/人工评分）三者**分开统计**，不得混作一个"通过率"。

**B. 质量与成本对比（真实模型，需预算）**

同一批业务任务（先用 5～6 个代表案例，再用全部 20 个）比较：

| 对比项 | 测量 |
|---|---|
| 交付质量 | 按发布门槛表：硬条件、成品率、引用可定位率、人工评分（1～5，四项 ≥4 的比例） |
| 与预期一致性 | 交付等级与案例预期（成品/草稿/无法完成）比对，partial 单列 |
| 成本与时延 | 每次运行的实际调用数、估算费用、墙钟时间；auto 臂必须**包含调度调用本身**并单列（次数/费用/时延），与 fixed 臂对比时不得剔除 |
| 过程可信度 | 子智能体产出是否都带来源与定位；是否存在无依据表述 |

对照臂：`fixed`（现有固定流程）、`auto`（调度智能体选型）、以及至少一个多智能体模式（如 `manager_worker`）。

公平性与统计纪律：三臂使用同一模型、同一批案例、同一份代码配置（仅执行方式不同）；每案例 repeats 视预算 1～2 次，波动进报告；**5～6 案例的小样本只做趋势判断与"明显劣化"否决，结论性门槛（是否切换默认模式）必须在全部 20 案例上复验**；结果以逐案例明细表呈现，不在小样本上下过强结论。对比基线一律用 S8-00 纠偏后的评测口径（关闭开卷、口径回归文档规定），否则数字不可信。

**C. 选型质量**

- 简单主题不得被过度编排（不能为了"用上多智能体"而多花 3 倍钱）。
- 复杂主题不得退化成单智能体（该并行/该审核的必须体现）。
- 度量草案：先离线建立**选型标注集**（≤10 个案例：复杂度特征 + 期望模式区间 + 标注理由，人工确认后冻结），S8-05 检查选型是否落在区间内；方案理由中的可验证断言（如"资料充足""有 N 个独立子题"）由程序对照实际输入核验，不一致记入报告。

**门槛**：不预设漂亮数字。先跑出三个对照臂的真实基线，再定默认模式与门槛；未达标就如实写"未达标"。

## 10. 风险与边界

- **成本失控**：多智能体天然更贵。缓解：默认最省模式、预算递减、派生数量上限、方案必须先给预计花费。
- **递归膨胀**：允许嵌套是用户明确要求，但必须靠深度/数量/去重三道锁；任何一道失效都可能烧钱。
- **把汇总当交付**：子智能体产出只是中间物，最终必须过成稿与审核，否则等于降低标准。
- **质量未必提升**：多智能体可能只是"更长的文本"。因此 S8-05 是决策点，没有证据就不改默认。
- **与最小权限冲突**：现有研究流程刻意不给工具；引入子智能体后要维持权限交集，且网页/资料中的指令仍不得改变权限。
- **选型被资料内容操纵**：资料/网页中的指令性文字若进入调度输入，可能诱导系统选高价模式或派生更多子任务。缓解：调度只看资料概况不看全文；调度提示词声明资料内容不是指令；选型结果不改变任何权限边界（与"网页指令不改权限"同一条红线）。
- **模式数量陷阱**：本计划不以"支持更多模式"为目标，模式是否被使用由选型与证据决定。

## 11. 暂不做

- 不做跨机器分布式执行、不做向量库/长期跨任务记忆、不做自动发布或对外写操作。
- 不开放无限嵌套、不开放用户自定义任意策略脚本。
- 不用"步骤跑完/角色数量/文本长度"代替业务验收。
